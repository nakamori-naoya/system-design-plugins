# システム設計

要求、利用・負荷、品質要求を先に明らかにし、その根拠からクラウドアーキテクチャを設計するClaude Code／Codex両対応のプラグインリポジトリです。公開インストール対象は`system-design@system-design`という単一パッケージです。

## 公開プレイブック

| プレイブック | `write-doc`へ渡す専用型 | 対応する一責務スキルと完了状態 |
|---|---|---|
| `discover-requirements` | `requirements-discovery` | 目的、責任範囲、制約に加え、サービス特性から失敗リスクと必要な成果を導く因果を、根拠と要求ID付きで記録する |
| `discover-workload-model` | `workload-model` | 調査結果を採用仮定へ変え、規模、到着率、偏り、保持を要件とインフラ構成の判断へ接続する設計入力モデルにする |
| `discover-quality-requirements` | `quality-requirements` | 業務影響を、対象、刺激、環境、期待応答、測定基準、測定方法を持つ品質シナリオにする |
| `design-cloud-architecture` | `cloud-architecture` | 要求・負荷・品質・制約から、選定、比較、ADR、編集可能な図、追跡表、検証計画を備えたクラウド設計を作る |

4つは個別実行できる独立入口であり、それぞれが同名の内部スキルへ明示的にルーティングします。同等の既存資料が入力契約を満たせば、先行プレイブックの実行を必須としません。入力不足が採用判断を変える場合も日本語Markdown正本は保存し、`status: unresolved`、未決一覧、`handoff.ready: false`を残します。未決を確定前提として後続へ渡しません。

複数成果物で共有する用語と暫定境界は、一つのMarkdown用語正本に定義し、要求、利用・負荷、クラウド構成のスキーマ2から用語正本の版・所在と日本語の推奨用語名を参照します。用語IDや用語正本IDを利用者へ要求せず、定義本文を各資料へ複製しません。用語正本は表にせず、`アクター`、`コマンド`、`クエリ`、`コマンドイベント`、`クエリイベント`、`時間イベント`、`システムイベント`、`値・指標`、`状態`、`データ`、`方針・制約`、`業務上の概念`、`負荷特性`、`設計上の概念`の概念種別見出しの下へ、推奨用語名を見出しとして置きます。状態変更の意図は`コマンド`、読み取り専用操作は`クエリ`、コマンド成功後の状態変更事実は`コマンドイベント`、状態を変えず読み取りが成立した事実は`クエリイベント`、時刻・期限への到達事実は`時間イベント`、内部処理の観測事実は`システムイベント`へ分けます。業務上の対象・関係・情報は`業務上の概念`、処理量や共有資源への負荷を増やす性質は`負荷特性`、測定値は`値・指標`へ分けます。要求発見のスキーマ2は操作台帳を持ち、コマンドとクエリから各成功イベントを別々に追跡し、開始／解除など対になる操作と未決の非成功結果を検査します。`plugins/system-design/scripts/terminology.py check --terminology <用語正本の絶対パス> --artifact <成果物の絶対パス>`は、複数成果物が同じ版・所在を参照すること、推奨用語名が存在すること、見出しの重複や概念種別の不整合がないことを検査します。

各プレイブックは、公開playbookの`grill`で入力だけでは決まらない点を推奨付きで1問ずつ確認し、`ground`で決定と未決を分離したまま根拠化します。その後、同名の一責務スキル、`material`、`verify`を通し、公開playbookの`write-doc`へ素材を渡して日本語Markdown正本を1本保存します。最終工程は成功時・失敗時のどちらでも走り、自分が所有する一時成果物だけを削除します。

## 責務境界

- プロダクトの北極星やプロダクト戦略をこのリポジトリで立案しません。
- 業務ルールやBDD、画面、API、論理DB、DDL、索引、IaCをクラウド都合で作りません。
- BDDへ渡す場合は、公開されたBDD入口への参照資料として、確定事項と仮説を区別したまま利用者が明示します。
- 外部パッケージは公開プレイブックパッケージとしてのみ依存でき、内部実装やインストール用キャッシュは実行時依存にしません。

## 配布構造

- Codex マーケットプレイス: `.agents/plugins/marketplace.json`
- Claude Code マーケットプレイス: `.claude-plugin/marketplace.json`
- 配布パッケージ: `plugins/system-design`
- 公開プレイブック: `plugins/system-design/playbooks/system-design`
- 内部の一責務スキル: `plugins/system-design/skills`

マーケットプレイスは実行時固有の根拠表現を使いますが、マーケットプレイス名、パッケージ名、版、配布先は検証スクリプトで同一性を保証します。

## プロバイダー実行設定

`design-cloud-architecture`プレイブックを開始する前に、対象リポジトリの`.harness-plugins/system-design.config.yml`でプロバイダーを明示します。`prepare-provider`、`resolve-provider`、設計、`finalize-provider`の順に実行し、設定層は統合せず、最優先の一ファイルが完全でなければ停止します。

```yaml
version: 1
cloud:
  provider: aws # AWS（機械値: aws）またはGCP（機械値: gcp）
instructions:
  architecture:
    directive: 設定済みプロバイダーを解決してからクラウドサービスを比較・選定する
```

同梱の`plugins/system-design/config/defaults.yml`はスキーマを示しますが、プロバイダー値は意図的に空です。未指定や`aws`／`gcp`以外を暗黙の既定値へ倒しません。`plugins/system-design/scripts/prepare.sh <対象リポジトリの絶対パス>`が返した解決済み設定パスを、アーキテクチャ正本の入力根拠へ残します。

## 英語表記の監査方針

- 機械互換のため維持するもの: スキルID、CLI、ファイル名、JSON／YAMLのキー・列挙値、参照ID、単位、数式、プロトコル。
- 英語が通例のため維持するもの: AWS、GCP、ADR、SLO、RPO、RTO、API、JSON、YAML、BDD、Mermaid、Terraform、95パーセンタイル表記の`p95`。初出で日本語の意味または機械値を併記します。
- 日本語化するもの: 見出し、説明、判断理由、典型例、反例、境界例、図の表示名、テストデータの人間向け文章。
- 判断保留: 現在はありません。将来、製品の正式名称を追加した場合は、正式名称を維持して役割を日本語で補います。

## 検証

`scripts/validate.sh`は、マーケットプレイスとマニフェストの同一性、4本の公開プレイブックと4個の内部スキル、明示ルーティング、工程順、依存境界、シンボリックリンクやソースのチェックアウトへの依存を検査します。`scripts/validate_repository.py --self-test`は、空のスキル集合、メタデータ不一致、契約節不足、不正な外部依存を意図的に作り、検証器が拒否することを確かめます。

公開スキルの実装が揃うまではリポジトリ検証が失敗する設計です。構造検査の成功、テストデータの静的検査、実モデルによる意味評価、実ツール端から端までの検証（E2E）は別の結果として報告します。
