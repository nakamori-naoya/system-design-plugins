# discover-workload-model

このskillを読み終えたagentは、調査結果を対象システムで採用する仮定へ変え、「誰のどの行為・イベントが、どの規模と時間的・分布的特性で発生するとして設計するか」を、要件とインフラ構成の判断へ接続した設計入力モデルとして保存できる。成果物は対象サービスの実情を紹介する調査報告ではない。応答時間、可用性、RPO、RTOなどのSLO、論理データモデル、インスタンス数、分割方式、キャッシュ、キュー、クラウドサービスは決めない。

工程順は[工程順序の正式な定義](playbook.yml)が定め、同じagentが`steps`を宣言順に実行する。`agent_work: invoking_agent`の工程はこのagentの認知工程、`script:`の工程は標準入力の本文と上流資料のpathから閉じた結果を返す決定論的tool、`playbook:`の工程は外部公開playbook（`grill`、`write-doc`）の直接呼び出しである。本文はインメモリで保持し、JSONも作業用fileも作らない。失敗した工程は成功扱いせず停止し、完了工程、根拠、未決を残す。再開時は最初の未完了工程から続ける。

## 入力

- 対象となる利用者、行為、イベントの一つ以上と、その対象期間。
- `requirements_document_path`。要求発見資料（requirements-discovery型のMarkdown）の絶対path。`REQ-` / `DRV-` / `CON-` / `REQ-HYP-` / `REQ-OQ-`の参照は要求発見資料のIDへ到達しなければならない。
- ユーザージャーニー、ドメイン成果物があれば、その絶対pathと版またはハッシュ（`journey_or_domain_artifacts`）。
- 観測値、予測、合意済み計画値の要求源。各値について根拠の所在情報と観測時点を識別できること。生成方法や固有形式は限定しない。
- `references`（任意）。追加で従う資料の絶対path配列。手順1で最初に読む。プロジェクト固有の規約や文脈（置き場、命名、用語、追加で従う資料）は、対象repositoryのAGENTS.md / CLAUDE.mdとこの`references`で渡される。
- `document_destination`。新規は`{output_directory, name}`、更新は`{update_target}`（既存の利用負荷モデル資料の絶対path）のどちらか一方。名前と置き場は利用者の既存資料構成に従い、依頼に無いときだけ`workload-model.md`を初回提案する。版は持たず、更新の履歴はgitが担う。

## 判断基準

| 観察対象 | 判定 |
|---|---|
| 数値根拠の分類 | 観測条件と時点があれば`fact`。決定者・対象・条件が揃えば`agreed_decision`。それ以外の予測・推定・暫定利用は`hypothesis`。利用者が暫定利用を認めても分類は変わらない |
| 根拠の種別 | 出典が公開資料なら`公開情報`、対象の観測なら`実測`、決定記録なら`利用者決定`、桁を置いた推定なら`推定`。`推定`は計算に式を持つ |
| 数値を受理できるか | 値、単位、時間窓、母集団、根拠ID、確からしさ、算出方法、検証計画、設計感度が揃えば受理。一つでも欠ければ`未決`にし、解消する未決の問いと測定方法を結ぶ |
| 定量情報が無いとき | 対象が識別できればフェルミ推定で桁を置き、定義・根拠種別・計算・時間窓・確度・再確認条件を持つ`hypothesis`にする。利用者／行為／イベントの対象自体が識別できなければ止まる |
| 平均・ピーク・突発 | それぞれ別の特性で、観測窓を持つ。合計件数から平均を出す式は活動時間か暦時間かを含む。平均への倍率だけで作ったピーク・突発は根拠が無いので`未決` |
| 偏りの型 | 短時間の操作集中（平均・ピーク・突発の到着率）で偏るなら操作頻度型。一操作からの処理増幅（fan-out、hot key）で偏るなら影響範囲型。分類名は対象サービスの言葉で中立に書き、利用者を不正と決めつける呼称は使わない |
| 適用範囲 | 世界規模など比較のための値は`世界規模の参照値`、初期実装の合格値として合意した値は`初期実装の合格値`、特定の集合に閉じた偏りは`局所負荷` |
| 設計入力になるか | 採用仮定が要件参照（`REQ-` / `DRV-` / `CON-`）と構成上の関心（容量・分割・非同期化・流量制御・保持・削除）へ接続され、適用範囲・確からしさ・見直し条件を持てば`DIN-`。接続できない数値は調査素材のまま設計入力へ昇格させない |
| 保持と消去 | 通常利用経路からの除外と、物理消去（削除・アーカイブ・匿名化・法的保全・複製やバックアップ）は別の判断として記録する |
| 問いの選定 | 要求源と上流成果物を読めば分かることは問わない。答えで母集団、到着率、保持、偏り、設計入力の接続が変わる問いだけを、成果を左右する順に選ぶ |

## 手順

### 1. 上流成果物と対象の同一性を固定する

`references`の資料、要求発見資料、ユーザージャーニー・ドメイン成果物を読む。各利用・負荷項目へ`WL-` IDを付け、種類を利用者・操作・イベントの一つにし、上流のIDを本文で引く。構成図のノード、表名、キュー名は利用者・行為・イベントではない。上流成果物の版が不明なら、読んだ内容のハッシュと観測時点を記録して進み、版の確認を推奨付きの未決の問いにする。対象の利用者／行為／イベントを識別できなければ止まる。

### 2. 数値根拠と状態を分ける

各出典へ`SRC-` IDを付け（調査根拠）、各数値を判断基準で分類する。業界平均、一般的な係数、別期間の値は対象の事実ではなく、必要なら仮説と検証計画へ明示する。

### 3. すべての数値へ測定文脈を付ける

[利用負荷モデルの契約](references/workload-contract.md)の「数値の完全性」を読む。値、単位、時間窓、母集団、根拠ID、確からしさ、算出方法、検証計画、設計感度を一組にする。直接観測は算出方法を「直接観測」と明記し、派生値は式、入力値、単位変換を記録する。一部の欠落は`未決`として切り離し、母集団または対象期間が利用負荷モデル資料全体で識別できないときだけ止まる。

### 4. 平均、ピーク、突発を別々に扱う

平均到着率、ピーク到着率、突発到着率を別特性へ置き、それぞれの時間窓を比較できるようにする。集中時間や時系列分布が無ければ未決の問いにする。

### 5. 比率、データ量、保持、成長を記録する

読み書き比を同じ母集団・時間窓で記録する。要求と応答のデータ量は単位付きで分ける。保持期間と増加率は現在量と別特性にし、増加率の基準期間を残す。期間上限に到達した後の定常状態と、通常利用経路からの除外・物理消去の区別を記録する。保持方針が未合意なら日数を決めず仮説または未決にする。

### 6. 偏りの型を分け、分布、配信先数、集中キーを記録する

[利用負荷モデルの契約](references/workload-contract.md)の「分布と増幅」を読む。判断基準に従い、偏りが操作頻度型か影響範囲型かを先に分ける。分布の形状、偏りの軸、観測または推定の要約を記録し、配信先数は一つの発生元から何配信先へ増幅されるか、集中キー割合は最上位キーまたはキー群へ集中する割合として、測定可能な入力特性で記録する。これらは特定のキャッシュ、キュー、partition、データベースを採用する理由ではない。該当する偏りが無い型は表に`なし`の行を置く。

### 7. 設計感度と検証計画を付ける

各指標の設計感度に「どの値域または不確かさが、どの判断の再検討を起こすか」を書き、検証方法、責任者、測定時点を未決の問いまたは検証計画へ残す。感度から決めるのは後続が比較すべき判断であり、インスタンス、サービス、分割数ではない。

### 8. 採用仮定を要件と構成判断へ接続する

[利用負荷モデルの契約](references/workload-contract.md)の「設計入力としての完了」を読む。関連する負荷項目を`DIN-` IDの設計入力へまとめ、根拠（種別と出典）、採用する仮定、適用範囲、要件への影響、構成への影響、見直し条件を記録する。各採用仮定について「この値を使って何を判断するか」と「この値を直接の合格値にしない範囲」を説明できる状態にする。

### 9. 成果を左右する問いをgrillで解消する

手順1〜8で残った未決のうち、判断基準「問いの選定」に従って問う候補を選び、それぞれに理由付きの推奨（フェルミ推定の桁を含む）を添えて`questions`にし、`topic`、`context`（purpose / audience / boundary）、`references`（入力の`references`をそのまま）とともに公開playbook `grill`へ渡す。問い方、上限、一覧への合意はgrillの公開契約に従う。

返った`decisions`は本文の該当箇所へ確定した根拠として反映する。返った`open_questions`は`state`が`open`なら推奨（`reason`）を仮置きし、本文の該当箇所へ`hypothesis`（測定文脈が揃わない値は`未決`のまま）として書き、「見直し条件と未決」へ`WL-HYP-` / `WL-OQ-`の行として推奨・根拠・採らなかった解釈・検証計画を書く。`fact`や`agreed_decision`へ昇格させない。`withdrawn`は取り下げ理由を本文に残す。

同じ実行でgrillを再び呼ぶのは、利用者が求めた場合か、その決定なしでは手順10の本文を組み立てられない場合だけである。それ以外の残った未決は、保存した成果物とともに推奨を添えて示し、利用者が成果物を見てから確かめる。

### 10. 本文を組み立てる

利用負荷モデル資料の本文を、write-docの`workload-model`型templateが示す論点に沿ってインメモリに組み立てる。更新では既存資料の見出し、語り口、参照されているanchorを優先する。新規では、結論と今回採用する値を先に置き、採用値ができるまで、平均とピーク、分布の偏りと処理の増幅、データ量・保持・増加、設計へ渡す境界、計算と仮定、未決を、対象に合う自然な見出しで書く。公開情報の説明から始めず、参照値、今回値、初期実装の検証境界を混同しない。IDと根拠状態はagentの評価では保持するが、本文へ出すのは後続資料との追跡に必要な場合だけとし、末尾の短い追跡情報へ置く。

### 11. 本文を検査する

本文を標準入力で、要求発見資料を`--upstream`で`scripts/workload.py`へ渡す。渡し方の例:

```bash
python3 scripts/workload.py check --upstream /absolute/path/to/requirements-discovery.md <<'MD'
# 利用・負荷モデル — <対象>
...本文...
MD
```

| 呼び出し | 入力 | 出力 | 失敗の観測 | 失敗時 |
|---|---|---|---|---|
| `python3 scripts/workload.py check --upstream <要求発見資料の絶対path> < <本文>` | 標準入力の本文と上流資料のpath（複数可） | 終了code 0、stdoutに`verified: true`、`status`（`ready` / `unresolved`）と本文にある追跡ID一覧のJSON | 終了code 2、stderrに`FAIL: <理由>`（入力欠落、上流資料を読めない、H1・冒頭段落・H2・各節本文の構造不備） | 手順10へ戻って本文を直す。数値の測定文脈、平均・ピーク・偏り・増幅・保持、要件と設計判断への接続はscriptの成功で代替せず、agentが上流資料と本文を読んで確かめる。理由が入力の欠落なら止まる |

用語定義との整合はこの型の利用負荷モデル資料ではscriptで検査しない。用語定義があるときは、本文の語が推奨用語名と一致するかを手順13でagentが読んで確かめる。

### 12. write-docへ渡して保存する

検査済み本文を`material: [{kind: text, content: <本文>}]`、`document_type: workload-model`、`document_destination`の保存先、`references`（入力の`references`をそのまま）として`write-doc`へ渡す。`status: completed`なら`path`を`workload_document_path`にする。`status: failed`なら`reason`をそのまま報告して停止する。

### 13. 読み戻して確かめる

保存した資料を全文読み、手順11で検査した本文と同じID、数値、根拠状態、未決、statusを保っていることを確かめる。欠落や昇格があれば`failed`として資料pathと理由を報告する。

## 停止条件

止まるのは次のときで、それ以外の判断の揺れや資料の不足では止まらない。

- 対象の利用者／行為／イベント、または母集団と対象期間を識別できず、負荷モデルの対象が無い。
- 要求発見資料が無い、または上流成果物が別の対象システムか別の利用行為を指しており、同一対象として扱えない。
- 依頼の中心がSLO、データモデル、技術方式、クラウド構成の決定で、負荷特性の発見目的が無い。責務外として返し、このskillの完了としない。
- `document_destination`が未指定、相対path、または両方式の併記で、保存先を確認できない。
- `grill`が`failed`を返した、`workload.py`が入力の欠落を理由に2を返し本文を直しても成り立たない、`write-doc`が失敗した。理由を変えずに返す。

止まるときは確認済みの値を残し、止めた換算または判断、必要な入力または確認、回答者または測定方法、影響するWL / DIN ID、再開条件を返す。

grillの回答・合意待ちは継続待ちであり、完了でも失敗でもない。待つ間は利用負荷モデル資料を保存しない。

判断の揺れや資料の不足では、その時点の根拠から最も筋の良い仮説を立てて進む。

- 定量情報が無い: フェルミ推定で桁を置き、定義・根拠種別・計算・時間窓・確度・再確認条件を持つ`hypothesis`にする。
- 単位、時間窓、母集団、根拠、確からしさの一部が欠ける: その指標を`未決`にし、解消する問いと測定方法を推奨付きで結ぶ。
- 上流成果物の版が不明: 読んだ内容のハッシュと観測時点を記録し、版の確認を未決の問いにする。
- 保持方針、分布、集中時間が未合意: 日数や形状を確定させず、`hypothesis`または`未決`として推奨を添える。

仮説は仮説と分かる形で利用負荷モデル資料に書き、平均をピークへ、未知を一様へ、仮説を事実へ変えない。

## 出力

- 利用負荷モデル資料: write-docが返した`workload_document_path`（workload-model型のMarkdown）。結論、採用値の由来、平均・ピーク・バースト、偏りと増幅、データ量・保持・増加、設計へ渡す境界、計算と未決を、読者が判断できる自然な構成で含む。追跡情報は後続連携に必要な場合だけ置く。JSON資料は持たない。
- 公開結果: `status`（`ready`または`unresolved`）、`decisions`、`open_questions`（推奨付き）、`hypotheses`、`workload_document_path`。
- 報告: 利用負荷モデル資料の絶対path、status、利用・負荷項目数、設計入力数、確認済み・仮説・未決の指標数、問うた問いと回答、推奨を仮置きした未決の問い、後続利用の可否、実行した検証（`workload.py`の結果）、未検証範囲。負荷試験は実行していないので、予測を実績として報告しない。

完了とは、資料が保存され読み戻しで検査済み本文と意味が一致し、statusが`ready`または`unresolved`であり、各採用仮定が適用範囲・要件参照・構成上の関心・確からしさ・見直し条件へ接続されていることをいう。

## 責務の外

SLOの決定、ユーザージャーニー、ドメインルール、BDD、論理データモデル、インスタンス数、分割数、データベース、キャッシュ、キュー、ストリーム、リージョン、クラウドサービス、IaCの選定は、このskillの成果物ではない。

## 後続成果物への追跡

「見直し条件と未決」の影響先に、品質とクラウド設計へ渡すWL、DIN、仮説、未決の問いのIDを記録する。ユーザージャーニーまたはドメインから再実行したときは`update_target`で利用負荷モデル資料を更新し、意味が変わったIDを黙って再利用しない。上流成果物または観測窓が変わったときは、以前のピーク、分布、増加率と後続のQR / ADRを再確認対象にする。
