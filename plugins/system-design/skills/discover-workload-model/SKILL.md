# discover-workload-model

このskillを読み終えたagentは、調査結果を対象システムで採用する仮定へ変え、「誰のどの行為・イベントが、どの規模と時間的・分布的特性で発生するとして設計するか」を、要件とインフラ構成の判断へ接続した設計入力モデルとして保存できる。成果物は対象サービスの実情を紹介する調査報告ではない。応答時間、可用性、RPO、RTOなどのSLO、論理データモデル、インスタンス数、分割方式、キャッシュ、キュー、クラウドサービスは決めない。

工程順は[工程順序の正本](playbook.yml)が正本で、同じagentが`steps`を宣言順に実行する。失敗した工程は成功扱いせず停止し、完了工程、根拠、未決を残す。再開時は最初の未完了工程から続ける。

## 入力

- 対象となる利用者、行為、イベントの一つ以上と、その対象期間。要求ID、ユーザージャーニーの場面ID、ドメインイベントIDがあれば、生成元成果物の絶対pathと版またはハッシュ。
- 観測値、予測、合意済み計画値の要求源。各値について根拠の所在情報と観測時点を識別できること。生成方法や固有形式は限定しない。
- 更新する場合は、既存の利用負荷モデル正本の絶対pathと現在の`artifact.version`。
- `document_destination`。新規は`{output_directory, name}`、更新は`{update_target}`のどちらか一方。名前と置き場は利用者の既存資料構成に従い、依頼に無いときだけ`workload-model.md`を初回提案する。
- 共有する用語や暫定閾値があるときは、一つのMarkdown用語正本の所在と版。

## 判断基準

| 観察対象 | 判定 |
|---|---|
| 数値根拠主張の分類 | 観測条件と時点があれば`fact`。決定者・対象・条件が揃えば`agreed_decision`。それ以外の予測・推定・暫定利用は`hypothesis`。利用者が暫定利用を認めても分類は変わらない |
| 数値を受理できるか | 値、単位、時間窓、母集団、根拠主張ID、確からしさ、算出方法、検証計画、設計感度が揃えば受理。一つでも欠ければ`unresolved`として`value: null`にし、解消する未決の問いと測定方法を結ぶ |
| 定量情報が無いとき | 対象が識別できればフェルミ推定で桁を置き、定義・根拠種別・計算・時間窓・確度・再確認条件を持つ`hypothesis`にする。対象自体が不明なら停止する |
| 平均・ピーク・突発 | それぞれ別の特性で、観測窓を持つ。合計件数から平均を出す式は活動時間か暦時間かを含む。平均への倍率だけで作ったピーク・突発は根拠が無いので`unresolved` |
| 偏りの型 | 短時間の操作集中（平均・ピーク・突発の到着率）で偏るなら操作頻度型。一操作からの処理増幅（`fan_out`、`hot_key_share`）で偏るなら影響範囲型。分類名は対象サービスの言葉で中立に書き、利用者を不正と決めつける呼称は使わない |
| 分布 | 分布を測定した根拠主張があるときだけ`shape: uniform`。無ければ`shape: unknown`で`unresolved` |
| 適用範囲 | 世界規模など比較のための値は`reference_scale`、初期実装の合格値として合意した値は`implementation_acceptance`、特定の集合に閉じた偏りは`localized_load` |
| 設計入力になるか | 採用仮定が要件参照または構成上の関心へ接続され、適用範囲・確からしさ・見直し条件・適用しない範囲を持てば`DIN-`。接続できない数値は調査素材のまま正本の設計入力へ昇格させない |
| 保持と消去 | 通常利用経路からの除外と、物理消去（削除・アーカイブ・匿名化・法的保全・複製やバックアップ）は別の判断として記録する |
| 質問の状態 | 回答を受理した問いは`resolved`、利用者が理由付きで取り下げた問いは`withdrawn`、未回答または未合意は`open` |

## 手順

### 1. 上流成果物と対象の同一性を固定する

各入力へ`SRC-` IDを付け、`kind`、絶対pathまたは再現可能な所在情報、版またはハッシュ、観測時点を記録する。各利用・負荷項目へ`WL-` IDを付け、種類を`actor`、`action`、`event`の一つにし、上流項目IDを`source_subject_refs`へ残す。構成図のノード、表名、キュー名は利用者・行為・イベントではない。上流成果物の版または対象が不明なら未決と影響先を返して停止する。共有語は用語正本の所在・版と推奨用語名を`terminology`へ記録し、定義本文は複製しない。

### 2. 数値根拠主張と状態を分ける

各数値根拠主張へ`CLM-` IDと対象特性を付け、判断基準で分類する。業界平均、一般的な係数、別期間の値は対象の事実ではなく、必要なら仮説と検証計画へ明示する。

### 3. すべての数値へ測定文脈を付ける

[利用負荷モデルの契約](references/workload-contract.md)の「数値の完全性」を読む。値、単位、時間窓、母集団、根拠主張ID、確からしさ、算出方法、検証計画、設計感度を一組にする。直接観測は算出方法を「直接観測」と明記し、派生値は式、入力値、単位変換を記録する。欠落が対象全体の意味を変えるときは保存前に停止する。

### 4. 平均、ピーク、突発を別々に扱う

平均到着率、ピーク到着率、突発到着率を別特性へ置き、それぞれの時間窓を比較できるようにする。集中時間や時系列分布が無ければ未決の問いにする。

### 5. 比率、データ量、保持、成長を記録する

`read_share`と`write_share`を同じ母集団・時間窓で記録し、確認済み値なら合計1を検査する。要求と応答のデータ量は単位付きで分ける。`retention_period`と`growth_rate`は現在量と別特性にし、増加率の基準期間を残す。期間上限に到達した後の定常状態と、通常利用経路からの除外・物理消去の区別を記録する。保持方針が未合意なら日数を決めず仮説または未決にする。

### 6. 偏りの型を分け、分布、配信先数、集中キーを記録する

[利用負荷モデルの契約](references/workload-contract.md)の「分布と増幅」を読む。判断基準に従い、偏りが操作頻度型か影響範囲型かを先に分ける。分布のshape、偏りの軸、観測または推定の要約を記録し、配信先数は一つの発生元から何配信先へ増幅されるか、集中キー割合は最上位キーまたはキー群へ集中する割合として、測定可能な入力特性で記録する。これらは特定のキャッシュ、キュー、partition、データベースを採用する理由ではない。

### 7. 設計感度と検証計画を付ける

各指標の`sensitivity`に「どの値域または不確かさが、どの判断の再検討を起こすか」を書き、検証方法、責任者、測定時点を未決の問いまたは検証計画へ残す。感度から決めるのは後続が比較すべき判断であり、インスタンス、サービス、分割数ではない。

### 8. 採用仮定を要件と構成判断へ接続する

[利用負荷モデルの契約](references/workload-contract.md)の「設計入力としての完了」を読む。関連する負荷項目を`DIN-` IDの設計入力へまとめ、根拠、採用する仮定、適用範囲、補完する要件ID、比較すべき構成上の関心、確からしさ、見直し条件、適用しない範囲を記録する。各採用仮定について「この値を使って何を判断するか」と「この値を直接の合格値にしない範囲」を説明できる状態にする。

### 9. 質問一覧と対話終了を明示確認する

決まらない事項は理由付きの推奨を添えて一問ずつ確認する。全問を聞いた後、`open`、`resolved`、`withdrawn`に分けた一覧、解決内容、撤回理由、影響先を提示し、一覧全体と対話終了の明示確認を得る。`open_questions`の各要素は`state`、`resolution`、`reason`を持ち、`resolved`だけが非空の`resolution`を持つ。`question_review`へ全質問ID、確認者、確認内容、`dialogue_complete: true`を記録する。全IDの一致と明示確認が揃って初めて保存へ進む。

### 10. JSON正本を検査して保存する

[利用負荷モデルの契約](references/workload-contract.md)のスキーマと不変条件に従って候補JSONを作り、このskill直下の`scripts/workload.py`で検査・保存する。

| 呼び出し | 入力 | 出力 | 失敗の観測 | 失敗時 |
|---|---|---|---|---|
| `python3 scripts/workload.py check --file <候補JSONの絶対path>` | 候補正本 | stdoutに候補の絶対path、stderr空 | 終了code 2、stderrに`FAIL: <理由>` | 理由を変えずに返して停止する。unknownをuniform、仮説を事実、平均をピークへ変えて通さない |
| `python3 scripts/workload.py write --repo <対象repositoryの絶対path> --slug <slug> --file <候補JSONの絶対path>` | 初回保存 | stdoutに保存先`<repo>/system-design/workloads/<slug>.workload.json`の絶対path | 同上 | 同上 |
| 上に`--expected-version <現在version>`を加える | 更新保存 | 同上。版は現在+1 | 版不一致は終了code 2 | 期待版を確認して停止する |

用語正本を参照したときは、package共有のtool`../../scripts/terminology.py`で参照の整合を検査する。

| 呼び出し | 入力 | 出力 | 失敗の観測 | 失敗時 |
|---|---|---|---|---|
| `python3 ../../scripts/terminology.py check --terminology <用語正本の絶対path> --artifact <保存したJSON正本の絶対path>`（`--artifact`は複数可） | 用語正本Markdownと参照側JSON | stdoutに用語正本の絶対path、stderr空 | 終了code 2、stderrに`FAIL: <理由>`（未解決の用語名、版・所在の不一致、見出しの重複、概念種別に無い用語） | 理由を変えずに返して停止する。用語の定義を正本へ複製して通さない |

### 11. 日本語Markdown正本の本文を組み立てる

保存したJSONと根拠資料から本文を組み立てる。冒頭は、誰がどの容量・方式の判断に使うか、採用する仮定は何か、どの値が未決で最大容量の根拠に使えないかを、読み手の既知の語で書いた段落にする。公開情報の説明から始めず、「採用する仮定」をDINごとに根拠／採用する仮定／適用範囲／要件への影響／構成への影響／見直し条件で先頭に置く。以降は要件とインフラ判断への接続、初期実装で検証する境界、利用行為と規模、分布・偏り・バースト（操作頻度型と影響範囲型を分ける）、データ量・保持・増加（除外と物理消去を分ける）、計算、調査根拠、見直し条件と未決の順に書く。成果物IDと版、JSON正本の絶対path、WL/指標ID、数値・単位・時間窓・母集団、未決、`handoff`を含める。JSON状態が`ready_for_downstream`なら`status: ready`、`saved_with_open_questions`なら`status: unresolved`と`handoff.ready: false`を本文へ書く。

### 12. write-docへ渡して保存する

本文を`material: [{kind: text, content: <本文>}]`、`document_type: workload-model`、`document_destination`の保存先として`write-doc`へ渡す。`status: completed`なら`path`を`workload_document_path`にする。`status: failed`なら`reason`をそのまま報告して停止する。

### 13. 読み戻して確かめる

保存した資料を全文読み、JSON正本のID、状態、根拠、数値、未決、handoffが欠落・昇格していないことを確かめる。欠落があれば`failed`として資料pathと理由を報告する。

## 停止条件

- 利用者／行為／イベントと対象期間の未決が、母集団または到着率の意味を変える。
- 数値の単位、時間窓、母集団、根拠、確からしさが欠落し、未決として切り離せない。
- 上流成果物の対象または版が食い違い、同一の利用行為か確認できない。
- `document_destination`が未指定、相対path、または両方式の併記である。
- 既存正本の版が指定された期待版と一致しない。
- 依頼の中心がSLO、データモデル、技術方式、クラウド構成の決定で、負荷特性の発見目的が無い。この場合は責務外として返し、このskillの完了としない。

停止時は確認済みの値を残し、止めた換算または判断、欠けた単位・時間窓・母集団・根拠・確からしさ、回答者または測定方法、影響するWL/指標ID、再開条件を返す。

## 出力

- JSON正本: `<対象repository>/system-design/workloads/<slug>.workload.json`（スキーマ2）。入力成果物、根拠主張、利用者／行為／イベントごとの12指標、分布、設計感度、設計入力、未決の問い、後続引き渡し、用語正本への参照を含む。旧スキーマの正本は参照資産として残せるが、現行入力や更新対象として受理しない。
- Markdown正本: write-docが返した`workload_document_path`。
- 公開結果: `status`、`questions`、`open_questions`、`resolved_questions`、`withdrawn_questions`、`question_review`、`handoff`、`workload_artifact_path`、`workload_document_path`。
- 報告: 正本の絶対path、成果物の状態と版、利用・負荷項目数、確認済み・仮説・未決の指標数、作業を止める問い、後続利用の可否、実行した検証、未検証範囲。負荷試験は実行していないので、予測を実績として報告しない。

完了とは、両正本が保存され読み戻しで意味が一致し、状態が`ready_for_downstream`または`saved_with_open_questions`であり、各採用仮定が適用範囲・要件参照・構成上の関心・確からしさ・見直し条件・適用しない範囲へ接続されていることをいう。

## 責務の外

SLOの決定、ユーザージャーニー、ドメインルール、BDD、論理データモデル、インスタンス数、分割数、データベース、キャッシュ、キュー、ストリーム、リージョン、クラウドサービス、IaCの選定は、このskillの成果物ではない。

## 後続成果物への追跡

`handoff.downstream`に品質とクラウド設計へ渡すWL、指標、設計入力、設計感度、未決の問いのIDを記録する。ユーザージャーニーまたはドメインから再実行したときは`input_artifacts`の版またはハッシュと`source_subject_refs`を更新し、意味が変わったIDを黙って再利用しない。上流成果物または観測窓が変わったときは正本版を上げ、以前のピーク、分布、growthと後続のQR/ADRを再確認対象にする。
