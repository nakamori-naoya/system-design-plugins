# discover-quality-requirements

このskillを読み終えたagentは、「どこで何を測り、どの母集団と時間窓で、どの閾値を満たせば品質要求を満たすか」を、根拠状態と利用・負荷との関係を保ったまま一つの品質要求正本にできる。クラウドプロバイダー、リージョン、サービス、データベース、キャッシュ、キュー、インスタンス、構成、IaCは選定しない。

工程順は[工程順序の正本](playbook.yml)が正本で、同じagentが`steps`を宣言順に実行する。`agent_work: invoking_agent`の工程はこのagentの認知工程、`script:`の工程は標準入力の本文と上流正本のpathから閉じた結果を返す決定論的tool、`playbook:`の工程は外部公開playbook（`grill`、`write-doc`）の直接呼び出しである。本文はインメモリで保持し、JSONも作業用fileも作らない。失敗した工程は成功扱いせず停止し、完了工程、根拠、未決を残す。再開時は最初の未完了工程から続ける。

## 入力

- 対象の利用者目的または業務結果と、対象システムの境界。
- `requirements_document_path`。要求発見正本の絶対path。`REQ-` / `DRV-` / `CON-`と上流の仮説・未決の参照はこの正本のIDへ到達しなければならない。
- `workload_document_path`。利用負荷モデル正本の絶対path。`WL-` / `DIN-`と負荷側の仮説・未決の参照はこの正本のIDへ到達しなければならない。無い場合も未決を保存できるが、負荷依存の閾値はアーキテクチャへ引き渡せる状態にしない。
- ユーザージャーニー、ドメイン成果物があれば絶対pathと版またはハッシュ（`journey_or_domain_artifacts`）。
- 品質についての合意、観測事実、仮説、規制・契約上の制約。各主張の根拠の所在情報、観測時点、決定者を識別できること。
- `references`（任意）。追加で従う資料の絶対path配列。手順1で最初に読む。プロジェクト固有の規約や文脈（置き場、命名、用語、追加で従う資料）は、対象repositoryのAGENTS.md / CLAUDE.mdとこの`references`で渡される。
- `document_destination`。新規は`{output_directory, name}`、更新は`{update_target}`（既存の品質要求正本の絶対path）のどちらか一方。名前と置き場は利用者の既存資料構成に従い、依頼に無いときだけ`quality-requirements.md`を初回提案する。版は持たず、更新の履歴はgitが担う。

入力の状態と版またはハッシュを捨てた転記は入力として完成扱いしない。

## 判断基準

| 観察対象 | 判定 |
|---|---|
| 品質根拠の分類 | 観測条件と時点があれば`fact`。決定者・対象・条件が揃えば`agreed_decision`。それ以外は`hypothesis`。過去の実績は目標ではなく、希望は合意ではなく、利用・負荷の仮説は事実ではない |
| 10区分の判定 | 対象に関係し、合意または仮説の値があれば`指定済み`。関係し得るが答えが無ければ`未決`（解く問いを引く）。対象境界から関係しないと言えるときだけ`非該当`（理由を書く）。語られなかったことは非該当の理由にならない |
| 測定可能か | 観測点、指標、演算子付き閾値と単位、時間窓、母集団、検証方法が揃えば`QR-`として`agreed_decision`または`hypothesis`。一つでも欠ければ既知項目を保持した`open_question`で閾値は`未決` |
| 合意状態 | 決定者と対象範囲を持つ`agreed_decision`だけが合意済みの根拠。業界標準、クラウドの仕様値、現在実績、利用・負荷値は根拠無しに閾値にならず、使うなら`hypothesis`にして誰がいつ合意または反証するかを持たせる |
| 利用・負荷との関係 | 合否または検証条件が規模・平均・ピーク・突発・分布・配信先数・集中キー・成長で変わるなら、対象と入力根拠にその`WL-` / `DIN-`を根拠状態付きで載せる。負荷側の仮説は仮説のまま渡す |
| 矛盾 | 両立しない値、母集団、時間窓、前提は`QCON-`として対立するID（2つ以上）と`open` / `resolved`状態を持つ。`open`の矛盾は解く問いの影響先から参照される。一方の数値の上書きは解消ではない |
| 問いの選定 | 上流成果物と根拠を読めば分かることは問わない。答えで観測点、閾値、母集団、時間窓、矛盾の解消、アーキテクチャへの引き渡しが変わる問いだけを、成果を左右する順に選ぶ |

## 手順

### 1. 上流成果物と品質根拠を固定する

`references`の資料、要求発見正本、利用負荷モデル正本、ユーザージャーニー・ドメイン成果物を読む。各入力を「対象と入力根拠」に上流IDと根拠状態付きで載せ、各品質根拠を判断基準で分類して品質区分へ結ぶ。`fact`か`agreed_decision`か判定できない主張は`hypothesis`に分類し、分類が閾値の合意状態を変えるなら推奨付きの未決の問いへ結ぶ。

### 2. 品質区分を一件ずつ判定する

[品質要求正本の契約](references/quality-contract.md)の「品質区分」を読む。応答時間、処理量、可用性、整合性、耐久性、復旧性、安全性、プライバシー、運用性、費用を一件ずつ、判断基準で`指定済み`、`未決`、`非該当`へ判定する。

### 3. 測定不能表現を観測可能な条件へ分解する

「高速」「高可用」「安全」「低コスト」のように合否を一意に観測できない表現は、一つの合否判断ごとに`QR-` IDを付け、観測点、指標、演算子付き閾値と単位、時間窓、母集団、検証方法へ分ける。元の表現は根拠に残す。異なる検証者が同じ観測から同じ合否を判定できる状態が完成である。

### 4. 数値の合意状態を保つ

閾値、許容障害量、割合、時間、件数、費用などの数値候補を判断基準で`agreed_decision`または`hypothesis`にし、仮説には確からしさ、検証方法、設計感度を持たせる。各合意済みから合意根拠へ、各仮説から仮説根拠へ戻れる状態にする。

### 5. 利用・負荷との対応と矛盾を記録する

[品質要求正本の契約](references/quality-contract.md)の「利用・負荷対応と矛盾」を読む。品質要求が依存する`WL-` / `DIN-`を対象と入力根拠と追跡へ記録し、両立しない値・母集団・時間窓・前提は`QCON-`矛盾へ記録する。ピークを平均で代用せず、時間窓や母集団の違いを保つ。

### 6. 後続設計へ渡す感度を記録する

QRごとに再検討を起こす値域、不確かさ、対象判断を仮説と未決の検証計画と影響先に書く。選択候補が入力にあれば設計案として後続へ返し、品質要求へ混ぜない。

### 7. 成果を左右する問いをgrillで解消する

手順1〜6で残った未決のうち、判断基準「問いの選定」に従って問う候補を選び、それぞれに理由付きの推奨を添えて`questions`にし、`topic`、`context`（purpose / audience / boundary）、`references`（入力の`references`をそのまま）とともに公開playbook `grill`へ渡す。問い方、上限、一覧への合意はgrillの公開契約に従う。

返った`decisions`は本文の該当箇所へ確定した根拠として反映する。返った`open_questions`は`state`が`open`なら推奨（`reason`）を仮置きし、推奨の閾値は`hypothesis`として本文へ書き、「仮説と未決」へ`QR-HYP-` / `QR-OQ-`の行として推奨・根拠・採らなかった解釈・検証計画を書く。測定条件が揃わないQRは推奨を添えても`open_question`のままにし、矛盾は一方の数値を上書きせず`open`のままにする。`agreed_decision`へ昇格させない。`withdrawn`は取り下げ理由を本文に残す。

同じ実行でgrillを再び呼ぶのは、利用者が求めた場合か、その決定なしでは手順8の本文を組み立てられない場合だけである。それ以外の残った未決は、保存した成果物とともに推奨を添えて示し、利用者が成果物を見てから確かめる。

### 8. 本文を組み立てる

品質要求正本の本文を、write-docの`quality-requirements`型のtemplateが定める記法（H2見出しの名前と順序、表の列、`QR-` / `QCON-` / `QR-HYP-` / `QR-OQ-`のID、分類の10語、閾値の`<演算子> <数値> <単位>`、根拠状態の機械値、品質区分の網羅の判定3語）でインメモリに組み立てる。冒頭は、誰がどの判断に使う品質要求か、どの合意と観測から始まり、何が測定可能で何が未決かを、読み手の既知の語で書いた段落にする。以降は対象と入力根拠、品質要求、品質区分の網羅、トレードオフと矛盾、仮説と未決、追跡、この資料に書かないものの順に書く。上流の未決を継続する行は上流のID（例`WL-OQ-001`）をそのまま使う。追跡の`ADR・図ノードID`は初回は`未作成`でよい。

### 9. 本文を検査する

本文を標準入力で、要求発見正本と利用負荷モデル正本を`--upstream`で`scripts/quality.py`へ渡す。渡し方の例:

```bash
python3 scripts/quality.py check --upstream /absolute/path/to/requirements-discovery.md --upstream /absolute/path/to/workload-model.md <<'MD'
# 品質要求正本 — <対象>
...本文...
MD
```

| 呼び出し | 入力 | 出力 | 失敗の観測 | 失敗時 |
|---|---|---|---|---|
| `python3 scripts/quality.py check --upstream <要求発見正本> --upstream <利用負荷モデル正本> < <本文>` | 標準入力の本文と上流正本のpath | 終了code 0、stdoutに`verified: true`、`status`（`ready` / `unresolved`）、QR / 測定可能QR / QCON / 仮説 / 未決のID一覧のJSON | 終了code 2、stderrに`FAIL: <理由>`（H2の集合と順序、ID一意性と参照到達、上流IDの未解決または`--upstream`欠落、分類と閾値の記法、10区分の網羅と判定の整合、`open`の矛盾・`未決`の区分が問いへ結ばれていない、全QRの追跡のどれか） | 手順8へ戻って本文を直す。検査を緩めず、曖昧な表現へ閾値を補わず、仮説を合意、負荷仮説を確認済みへ変えて通さない。理由が入力の欠落（上流正本が無い等）なら止まる |

用語正本との整合はこの型の正本ではscriptで検査しない。用語正本があるときは、本文の語が推奨用語名と一致するかを手順11でagentが読んで確かめる。

### 10. write-docへ渡して保存する

検査済み本文を`material: [{kind: text, content: <本文>}]`、`document_type: quality-requirements`、`document_destination`の保存先、`references`（入力の`references`をそのまま）として`write-doc`へ渡す。`status: completed`なら`path`を`quality_document_path`にする。`status: failed`なら`reason`をそのまま報告して停止する。

### 11. 読み戻して確かめる

保存した資料を全文読み、手順9で検査した本文と同じID、測定条件、根拠状態、未決、statusを保っていることを確かめる。欠落や昇格があれば`failed`として資料pathと理由を報告する。

## 停止条件

止まるのは次のときで、それ以外の判断の揺れや資料の不足では止まらない。

- 対象の利用者目的または業務結果と対象システムの境界を識別できず、品質要求の対象が無い。
- 要求発見正本が無い。
- 依頼の中心がクラウド・製品選定、論理データ設計、IaC、配置で、品質要求発見の目的が無い。責務外として返し、このskillの完了としない。
- `document_destination`が未指定、相対path、または両方式の併記で、保存先を確認できない。
- `grill`が`failed`を返した、`quality.py`が入力の欠落を理由に2を返し本文を直しても成り立たない、`write-doc`が失敗した。理由を変えずに返す。

止まるときは確認済み根拠と測定条件を残し、止めた判断、必要な入力または確認、回答者または検証者、影響するQR / QCON ID、再開条件を返す。

grillの回答・合意待ちは継続待ちであり、完了でも失敗でもない。待つ間は正本を保存しない。

判断の揺れや資料の不足では、その時点の根拠から最も筋の良い仮説を立てて進む。

- 観測点、指標、母集団に複数の解釈があり得る: 最も筋の良い解釈で`QR-`を起こし、閾値は`hypothesis`にし、採らなかった解釈を推奨付きの未決の問いへ残す。
- 根拠の状態、観測時点、決定者が無い: `hypothesis`に分類し、誰がいつ合意または反証するかを未決の問いにする。
- 利用・負荷モデルが無い、または指標が未決: 負荷依存のQRを`open_question`にし、負荷側の未決を継続行として引き、`status: unresolved`で保存する。
- 測定条件の一部が欠ける: そのQRを`open_question`（閾値`未決`）にし、欠けた項目と検証者を推奨付きの未決の問いへ結ぶ。

仮説は仮説と分かる形で正本に書き、業界標準や現在実績を根拠無しに合意済みへ変えない。

## 出力

- 正本: write-docが返した`quality_document_path`（quality-requirements型のMarkdown）。対象と入力根拠、測定可能な品質要求、10区分の網羅、トレードオフと矛盾、仮説と未決、追跡を含む。JSON正本は持たない。
- 公開結果: `status`（`ready`または`unresolved`）、`decisions`、`open_questions`（推奨付き）、`hypotheses`、`quality_document_path`。
- 報告: 正本の絶対path、status、合意済み・仮説・未決件数、未解消矛盾、問うた問いと回答、推奨を仮置きした未決の問い、アーキテクチャへ引き渡せるか、実行した検証（`quality.py`の結果）、未検証範囲。負荷試験、障害試験、セキュリティ試験、費用計測は実行していないので、未実施の検証を合格として報告しない。

完了とは、正本が保存され読み戻しで検査済み本文と意味が一致し、statusが`ready`または`unresolved`であり、10区分が評価され、合意済みまたは仮説の品質要求が測定条件を持つことをいう。`unresolved`は保存完了であり、未決または未解消の矛盾の影響先をアーキテクチャへ引き渡せることを意味しない。

## 責務の外

ユーザージャーニーの場面、ドメインルール、要求、利用・負荷の値の創作や変更、クラウドプロバイダー、サービス、リージョン、可用性ゾーン、データベース、キャッシュ、キュー、インスタンス、ネットワーク、構成図、IaC、論理データモデル、API、画面の設計は、このskillの成果物ではない。

## 後続成果物への追跡

「追跡」と「仮説と未決」にアーキテクチャへ渡すQR、QCON、未決の問いのIDを記録する。後続は正本の絶対pathとQRの根拠状態、矛盾の状態を引用し、仮説を合意済み前提へ変えない。ユーザージャーニー、ドメイン、要求、利用・負荷の意味が変わったときは`update_target`で正本を更新し、影響するQR / QCONを再確認対象にする。既存IDを別の観測対象、時間窓、母集団へ再利用しない。
