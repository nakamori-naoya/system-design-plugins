# 要件の資料で外しやすい判断

## 要求にできるのは、合意された観測があるものだけ

`REQ-` は受益者が得る成果の単位に付け、資料の検討範囲や作成作業には付けない。受益者、必要な成果、合意済みの成功の観測、検証方法が揃い、根拠が `fact` か `agreed_decision` だけのものを要求にする。一つでも欠けるか、根拠に仮説や未決が混ざれば、`REQ-HYP-` か `REQ-OQ-` に置く。具体的な文章でも、根拠が仮説なら要求にしない。

複数の入力を一つの要件へまとめる前に、各主張の行き先を確かめる。要求にしない仮説、未決、方式の候補も消さず、どの成果や境界がその答えで変わるかを残す。後から一つにまとめた文章を読み返すだけでは、落とした主張に気づけないからである。

入力の「ここまでは決まったが、その先は未決」という境界を、広い言い方で消さない。各要求を元の条件と突き合わせ、本文・追跡の表・未決が互いに矛盾しないか確かめる。

追跡の表は参照の索引にとどめる。各 `REQ-` が誰にどの結果を返し、何を観測してどう確かめるかは、該当する本文で一組にして書く。表の短文や資料全体の完了条件だけでは、個々の要求を検証できない。仮説と未決も、後続で選ぶ理由と結論への影響は本文で読めるようにする。

事実は現在地の観測であり、将来の受入目標ではない。「利用者の30%が申請結果を電話で確かめた」は事実だが、「電話確認をゼロにする」はまだ合意された目標ではない。「申請者が当日中に結果を確かめられる」も、担当者の希望なら仮説で、決める人が対象と期限を指定して合意したときに初めて合意になる。変わるのは合意の有無であって、文章の具体性ではない。

成功と失敗は、誰が何を観測でき、何が変わらないかで書く。画面の表示や API の応答そのものは業務結果ではないが、利用者が確認する経路として入力が指定したものは消さない。

## 導出要件は、特性から必要な成果までの因果で書く

入力にそのまま書かれていなくても、サービスの特性から避けるべき失敗が導けるなら要件にする（`DRV-`）。特性（根拠の ID と状態）、それで誰に何が起きるか、手段を外しても成り立つ必要な成果、後続が比べる設計上の関心、見直す条件を一つの因果として本文に書く。

特性の値そのものは利用負荷の資料が、守る閾値は品質要求の資料が持つ。要件の資料では、その ID を引いて因果を要約し、実装の方式や設定値を必要な成果にしない。引く資料がまだ無ければ、特性を値のない言葉で示し、値は持ち主の資料で決める論点として送る。値を写すと、後に二か所の判断が食い違うからである。

## 設計判断に残すのは、合意済みか不可避なものだけ

`DEC-` に置けるのは、利用者が合意した方式か、確かめた導出要件から論理的に避けられない方式だけで、採用の理由と見直す条件を添える。「よく使われる」「速そう」は理由にならない。利用者の選択で方式が変わるなら、判断に入れず後続で決める論点へ送る。

同じ方式でも、提案なら仮説、決める人が対象と時点を指定した必須の決定なら固定制約（`CON-`）である。制約にしても、その方式を受益者の目的へ置き換えない。

## 範囲は、実装できるかで閉じる

提供する価値、今回実装するもの、設計だけを示すもの、対象外を分け、期間、使える基盤、手元で再現する範囲の予算を書く。比較に用いる規模を、初期実装の合格値へ黙って昇格させない。所有者の決まっていない責任を、対象システムへ寄せない。

操作は、状態を変える意図か読むだけかが利用者の判断を変えるときだけ分けて書く。成功だけでなく、拒否や無変更が利用者の成果を変えるなら、その境界も根拠に照らして扱う。
