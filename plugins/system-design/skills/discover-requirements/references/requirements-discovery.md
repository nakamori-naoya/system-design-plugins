# 要件の資料で外しやすい判断

## 要件として言い切れるのは、決めた人がいるものだけ

受益者、得る結果、成功したと確かめる観測が揃い、決めた人が対象と時点を指定したものだけを、要件として言い切る。一つでも欠けるか、根拠が推定や提案なら、見立てであることを文の言い方で示し、「まだ決まっていないこと」へ、何が分かれば決まるかと組にして置く。具体的な文でも、根拠が推定なら要件にしない。

事実は現在地の観測であり、将来の目標ではない。「利用者の30%が申請結果を電話で確かめた」は事実だが、「電話確認をゼロにする」はまだ決まった目標ではない。「申請者が当日中に結果を確かめられる」も、担当者の希望なら見立てで、決める人が対象と期限を指定して初めて要件になる。変わるのは合意の有無であって、文の具体性ではない。

複数の入力を一つの要件にまとめる前に、各主張の行き先を確かめる。要件にしない見立て、未決、方式の候補も消さず、どの結果や範囲がその答えで変わるかを残す。後から一つにまとめた文を読み返すだけでは、落とした主張に気づけないからである。入力の「ここまでは決まったが、その先は未決」という境界を、広い言い方で消さない。

成功と失敗は、誰が何を観測でき、何が変わらないかで書く。画面の表示や API の応答そのものは業務の結果ではないが、利用者が確かめる経路として入力が指定したものは消さない。

## 特性から導いた要件は、特性から結果までの因果で書く

入力にそのまま書かれていなくても、サービスの特性から避けるべき失敗が導けるなら要件にする。特性、それで誰に何が起きるか、手段を外しても成り立つ結果、何が変われば見直すかを、一続きの因果として本文に書く。

特性の値（規模、ピーク、偏り）と守る目標（速さ、上限）は、非機能要件の資料が持つ。要件の資料では、その資料へリンクして因果を要約し、値を写さない。非機能要件の資料がまだ無ければ、特性を値の無い言葉で示し、値はその資料で決める論点として送る。

## 手段は、固定された制約と、後で選ぶものに分ける

入力にある製品名、クラウド名、データベース、キュー、画面、API は要件ではない。決めた人が範囲と時点を決めた必須の条件なら「前提にする制約」に置き、提案や後で比べる候補なら要件に入れず、後の設計で決める論点として送る。制約にしても、その方式を受益者の目的へ置き換えない。

## 範囲は、作れるかで閉じる

今回作るもの、設計だけを示すもの、作らないものを分け、期間、使える基盤、予算を書く。比較に使う規模を、最初の公開の合格値へ黙って格上げしない。持ち主の決まっていない責任を、対象のシステムへ寄せない。
