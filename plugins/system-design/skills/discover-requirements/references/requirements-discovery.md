# 要件の資料で外しやすい判断

## 要求にできるのは、合意された観測があるものだけ

`REQ-` にできるのは、受益者、必要な成果、合意済みの成功の観測、検証方法が揃い、根拠が `fact` か `agreed_decision` だけのものである。一つでも欠けるか、根拠に仮説や未決が混ざれば、`REQ-HYP-` か `REQ-OQ-` に置く。具体的な文章でも、根拠が仮説なら要求にしない。

事実は現在地の観測であり、将来の受入目標ではない。「利用者の30%が申請結果を電話で確かめた」は事実だが、「電話確認をゼロにする」はまだ合意された目標ではない。「申請者が当日中に結果を確かめられる」も、担当者の希望なら仮説で、決める人が対象と期限を指定して合意したときに初めて合意になる。変わるのは合意の有無であって、文章の具体性ではない。

成功と失敗は、誰が何を観測できるかで書く。画面の表示、API の応答、使う技術は業務結果ではない。

## 導出要件は、特性から必要な成果までの因果で書く

入力にそのまま書かれていなくても、サービスの特性から避けるべき失敗が導けるなら要件にする（`DRV-`）。特性（根拠の ID と状態）、それで誰に何が起きるか、手段を外しても成り立つ必要な成果、後続が比べる設計上の関心、見直す条件を一つの因果として本文に書く。

特性の値そのものは利用負荷の資料が、守る閾値は品質要求の資料が持つ。要件の資料では、その ID を引いて因果を要約するだけにする。たとえば「一部の発生元だけ配信先が桁違いに多い（利用負荷の `WL-003`）ので、一つの操作の処理の増幅を通常の利用者へ波及させない」と書き、配信先数の計算やキューの製品は書かない。冪等キー、エラーコード、再試行の回数を必要な成果として書くのは、実装の詳細を要件へ逆流させている。

## 設計判断に残すのは、合意済みか不可避なものだけ

`DEC-` に置けるのは、利用者が合意した方式か、確かめた導出要件から論理的に避けられない方式だけで、採用の理由と見直す条件を添える。「よく使われる」「速そう」は理由にならない。利用者の選択で方式が変わるなら、判断に入れず後続で決める論点へ送る。

同じ「Redis を使う」でも、提案なら仮説、決める人が対象と時点を指定した必須の決定なら固定制約（`CON-`）である。制約にしても、Redis を受益者の目的へ置き換えない。

## 範囲は、実装できるかで閉じる

提供する価値、今回実装するもの、設計だけを示すもの、対象外を分け、期間、使える基盤、手元で再現する範囲の予算を書く。世界規模の設計の説明を、初期実装の合格値へ黙って昇格させない。所有者の決まっていない責任を、対象システムへ寄せない。

操作は、状態を変える意図か読むだけかが利用者の判断を変えるときだけ分けて書く。開始と解除、登録と取消のように対になる操作は、片方だけ書かれていないかを反証し、業務上無いならその理由を、判断できなければ未決を残す。無変更、拒否、失敗の扱いが根拠から決まらないときは、状態やコードを決めずに未決にする。
