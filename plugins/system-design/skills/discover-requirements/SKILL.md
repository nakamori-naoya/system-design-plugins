# discover-requirements

このskillを読み終えたagentは、依頼と要求源から一つの要求発見正本を作り、確認済み要求、導出要件、理由付き設計判断、未決を後続の負荷・品質・クラウド設計へ渡せる。判断は「観測事実・仮定 → 明示要件・固定制約 → 導出要件 → 設計判断 → 実装詳細」の五段階で境界を引く。要求発見は導出要件まで進み、設計判断は明示・不可避・合意済みのものだけを残し、実装詳細は後続へ送る。

工程順は[工程順序の正本](playbook.yml)が正本で、同じagentが`steps`を宣言順に実行する。失敗した工程は成功扱いせず停止し、完了工程、根拠、未決を残す。再開時は最初の未完了工程から続ける。

## 入力

- 依頼。対象、困りごとまたは望む結果、要求源の所在を識別できること。
- 利用者が明示した資料、観測結果、決定記録。各要求源について参照位置と観測時点または版を記録できること。要求源が依頼本文だけなら、根拠を「依頼本文」と記録する。
- 更新する場合は、既存の要求発見正本の絶対pathと現在の`artifact.version`。
- `document_destination`。新規は`{output_directory, name}`（既存の書き込み可能な絶対directoryと`.md`名）、更新は`{update_target}`（既存Markdownの絶対path）のどちらか一方。名前と置き場は利用者の既存資料構成に従い、依頼に無いときだけ`requirements-discovery.md`を初回提案する。
- 複数成果物で共有する用語があるときは、一つのMarkdown用語正本の所在と版。無ければ用語正本の所有者と配置を一問で確認する。

入力中の製品名、クラウド名、データベース、キュー、キャッシュ、画面、API、実装方法は要求ではなく、手順4で制約・仮説・設計案のどれかに分類する。

## 判断基準

| 観察対象 | 判定 |
|---|---|
| 根拠主張の分類 | 観測条件と時点があれば`fact`。決定者・対象・条件が揃えば`agreed_decision`。未検証の予測・期待・提案・推定は`hypothesis`。回答が無く要求または境界の意味を変える問いは`open_question` |
| 要求に昇格できるか | 根拠が`fact`または`agreed_decision`だけで、受益者、合意済み成功観測、検証方法、影響が揃えば`REQ-`。一つでも欠けるか根拠に仮説・未決を含めば仮説または未決のまま |
| Howの置き場 | 決定権者・対象範囲・決定時点が揃った必須手段は`constraint`。望む結果を満たすか未検証の手段は`hypothesis`。比較・選定を後続へ委ねる候補は`design_proposal`として`routed_to`へ送る |
| 導出要件になるか | 実現手段を外しても成り立つ「避けるべき結果と必要な成果」であれば`DRV-`。製品名、RPC項目、エラーコード、表、キュー、再試行回数を含む記述は実装詳細として後続へ送る |
| 導出要件の確からしさ | 確定事実または合意済み決定だけから導ければ`confirmed`。推定を含めば`hypothesis` |
| 設計判断を残すか | 利用者が合意した方式、または確認済み導出要件から論理的に不可避な方式だけ`design_decisions`へ。それ以外の方式は`solution_inputs` |
| 操作の種別 | 状態変更を意図する操作は`commands`、読み取り専用は`queries`。コマンド成功の事実はコマンドイベント、読み取り成立の事実はクエリイベント、時刻・期限到達の事実は時間イベント、内部処理の観測事実はシステムイベント |
| 対になる操作 | 開始／解除、登録／取消の対があれば相互参照、無ければ非該当理由、判断できなければ未決の問い |
| スコープ | 対象内と対象外が同じ意味を含まず、対象システムと外部主体の責任境界を説明できる。`scope_budget`で実装必須・設計説明のみ・対象外・実現上の制約を分ける |
| 用語 | 共有語は用語正本の所在・版と日本語の推奨用語名だけを参照する。定義本文は正本へ複製しない |
| 質問の状態 | 回答を受理した問いは`resolved`、利用者が理由付きで取り下げた問いは`withdrawn`、未回答または未合意は`open` |

## 手順

### 1. 要求源を根拠主張単位に分ける

各根拠主張へ`CLM-` IDを付け、`statement`、`source`、`observed_at`、`owner`を記録し、判断基準で分類する。後続のすべての項目が一つ以上の根拠主張IDへ戻れる状態にする。所在・時点・責任者が欠ける主張は、欠けた情報と影響先を未決として残す。

### 2. 受益者、目的、観測を分ける

受益者とその他のステークホルダーを分け、目的を「誰が、どの状態から、どの業務結果を必要とするか」で記録する。成功と失敗は、誰が何を観測できるかとして別々に記録する。画面表示、API応答、利用技術は業務結果ではない。観測主体または結果が決まらなければ、その一点を問うて停止する。

### 3. スコープとシステム境界を確定・保留し、スコープ予算で閉じる

`scope.in`、`scope.out`、対象システムの責任、外部主体の責任を列挙する。規制、契約、組織、技術の制約は要求や目的と分けて制約にする。実装期間、チーム規模、利用できる外部基盤、ローカルで再現する範囲、実装して検証する範囲を確認し、`scope_budget`で実装必須・設計説明のみ・対象外・実現上の制約へ分ける。所有者が未決の責任は対象システムへ寄せず、境界を変える未決は影響IDと停止する後続判断を付けて未決の問いにする。

### 4. 入力中のHowを分類する

[要求発見正本の契約](references/requirements-contract.md)の「Howの分類」を読み、判断基準に従って`constraint`、`hypothesis`、`design_proposal`へ分け、原文、分類理由、根拠主張ID、送付先、対応IDを追跡できるようにする。決定か提案か判定できず分類で要求または後続設計が変わるときは、その違いだけを確認する一問を返して停止する。

### 5. 確認済み要求を作る

一つの必要性ごとに`REQ-` IDを付け、受益者ID、合意済み成功観測ID、検証方法、満たした影響、満たさない影響、後続で影響する関心を持たせる。各要求から根拠、受入観測、検証方法、影響へ双方向に辿れる状態にする。

### 6. コマンド、クエリ、イベントを棚卸しする

[要求発見正本の契約](references/requirements-contract.md)の「操作とイベントの分類」を読む。対象内の各操作を判断基準の種別へ分け、各コマンドから成功時のコマンドイベントと業務上の状態変化の前後、各クエリから状態変更を伴わないクエリイベントを追跡できるようにする。対になる操作を反証し、対象内・対象外・未決のどれかを明示する。無変更、拒否、失敗の扱いが根拠から決まらないときは、状態・コード・再試行方法を決めずに未決の問いへ結ぶ。

### 7. サービス特性から導出要件を作る

[要求発見正本の契約](references/requirements-contract.md)の「導出要件と設計判断」を読む。負荷、保持、分布の偏り、整合性、障害波及、再試行などのサービス特性が明示要求だけでは表せない失敗を生むとき、一つの因果ごとに`DRV-` IDを付け、`サービス特性 → 失敗リスク → 必要な成果 → 設計影響 → 見直し条件`を一段ずつ記録する。定量情報が無ければフェルミ推定で桁を置き、定義・根拠種別・計算・時間窓・確度・再確認条件を持つ仮説として記録する。

### 8. 理由付き設計判断と実装詳細を分離する

判断基準に従い、`design_decisions`には根拠、導出要件、採用理由、見直し条件、後続責務を付ける。「よく使われる」「高性能そう」は理由にならない。利用者の選択で方式が変わるときは一問を返して停止する。

### 9. 質問一覧と対話終了を明示確認する

決まらない事項は理由付きの推奨を添えて一問ずつ確認する。全問を聞いた後、`open`、`resolved`、`withdrawn`に分けた一覧、解決内容、撤回理由、影響先を提示し、一覧全体と対話終了の明示確認を得る。`open_questions`の各要素は`state`、`resolution`、`reason`を持ち、`resolved`だけが非空の`resolution`を持つ。`question_review`へ全質問ID、確認者、確認内容、`dialogue_complete: true`を記録する。全IDの一致と明示確認が揃って初めて保存へ進む。

### 10. JSON正本を検査して保存する

[要求発見正本の契約](references/requirements-contract.md)のスキーマと不変条件に従って候補JSONを作り、このskill直下の`scripts/requirements.py`で検査・保存する。

| 呼び出し | 入力 | 出力 | 失敗の観測 | 失敗時 |
|---|---|---|---|---|
| `python3 scripts/requirements.py check --file <候補JSONの絶対path>` | 候補正本 | stdoutに候補の絶対path、stderr空 | 終了code 2、stderrに`FAIL: <理由>` | 理由を変えずに返して停止する。分類・未決・受入観測を昇格させて通さない |
| `python3 scripts/requirements.py write --repo <対象repositoryの絶対path> --slug <slug> --file <候補JSONの絶対path>` | 初回保存 | stdoutに保存先`<repo>/system-design/requirements/<slug>.requirements.json`の絶対path | 同上 | 同上 |
| 上に`--expected-version <現在version>`を加える | 更新保存 | 同上。版は現在+1 | 版不一致は終了code 2 | 期待版を確認して停止する。無条件上書きはしない |

用語正本を参照したときは、package共有のtool`../../scripts/terminology.py`で参照の整合を検査する。

| 呼び出し | 入力 | 出力 | 失敗の観測 | 失敗時 |
|---|---|---|---|---|
| `python3 ../../scripts/terminology.py check --terminology <用語正本の絶対path> --artifact <保存したJSON正本の絶対path>`（`--artifact`は複数可） | 用語正本Markdownと参照側JSON | stdoutに用語正本の絶対path、stderr空 | 終了code 2、stderrに`FAIL: <理由>`（未解決の用語名、版・所在の不一致、見出しの重複、概念種別に無い用語） | 理由を変えずに返して停止する。用語の定義を正本へ複製して通さない |

### 11. 日本語Markdown正本の本文を組み立てる

保存したJSONと根拠資料から、読み手が判断に使う本文を組み立てる。冒頭は、誰が何を合意するための正本か、どの観測と合意から始まり、何が確定して何が未決なら後続へ渡せるかを、読み手の既知の語で書いた段落にする。以降は因果順に、サービス特性と導出要件（DRVごとに特性 → 失敗リスク → 必要な成果 → 設計影響 → 見直し条件）、負荷・偏りの暫定分類（対象サービスの言葉で中立に）、理由付き設計判断、保持期間と期間上限後の定常状態、固定制約、スコープの4区分と予算、コマンドとクエリ、用語正本の所在と版、後続設計で決める論点、観測可能な完了の順に書く。成果物IDと版、JSON正本の絶対path、根拠と要求ID、仮説、未決、`handoff`を本文に含める。JSON状態が`ready_for_downstream`なら`status: ready`、`saved_with_open_questions`なら`status: unresolved`と`handoff.ready: false`を本文へ書く。

### 12. write-docへ渡して保存する

本文を`material: [{kind: text, content: <本文>}]`、`document_type: requirements-discovery`、`document_destination`の保存先（`output_directory`と`name`、または`update_target`）として`write-doc`へ渡す。結果が`status: completed`なら`path`を`requirements_document_path`にする。`status: failed`なら`reason`をそのまま報告して停止し、部分保存を完成文書として扱わない。

### 13. 読み戻して確かめる

保存した資料を全文読み、JSON正本のID、状態、根拠、未決、handoffが欠落・昇格していないことを確かめる。欠落があれば`failed`として資料pathと理由を報告する。

## 停止条件

- 受益者、目的、対象システムの責任範囲の未決が要求の意味を変える。
- 要求源の参照位置または状態が分からず、事実・判断・仮説を区別できない。
- Howが合意済み制約か未決の提案か判定できず、分類によって要求または後続設計が変わる。
- `document_destination`が未指定、相対path、または両方式の併記である。
- 既存正本の版が指定された期待版と一致しない。
- 依頼の中心がユーザージャーニー、ドメイン、データモデル、技術方式、クラウド選定で、要求発見の目的が無い。この場合は要求発見を完了と報告せず、該当しない理由と適切な別入口を返す。

停止時は確定した根拠主張を残し、止めた判断、決めるための一問、回答者または確認方法、影響するID、再開に必要な入力を返す。

## 出力

- JSON正本: `<対象repository>/system-design/requirements/<slug>.requirements.json`（スキーマ2）。根拠主張、受益者・ステークホルダー、目的、成功・失敗の観測、範囲とスコープ予算、システム境界、制約、確認済み要求、操作台帳、導出要件、理由付き設計判断、判断履歴、用語正本への参照、仮説、未決の問い、手段指定の分類、後続への引き渡しを含む。旧スキーマの正本は参照資産として残せるが、現行入力や更新対象として受理せず、スキーマ2の新規成果物として一括作成する。
- Markdown正本: write-docが返した`requirements_document_path`。
- 公開結果: `status`、全状態を含む`questions`、`open_questions`、`resolved_questions`、`withdrawn_questions`、`question_review`、`handoff`、`requirements_artifact_path`、`requirements_document_path`。JSONだけ、またはMarkdownだけの保存は完了ではない。
- 報告: 正本の絶対path、成果物の状態と版、確認済み要求数、仮説数、作業を止める問い、後続利用の可否、実行した検証、未検証範囲。

完了とは、両正本が保存され読み戻しで意味が一致し、成果物状態が`ready_for_downstream`または`saved_with_open_questions`であることをいう。`saved_with_open_questions`は保存完了であり、作業を止める問いの影響先が後続利用可能であることを意味しない。

## 責務の外

ユーザージャーニー、ユースケース、ドメインルール、BDDシナリオ、エンティティ、論理表、列、キー、DDL、索引、画面、API、構成要素、技術方式、クラウド・サービス、リージョン、IaC、利用負荷や品質目標の値、プロダクトの北極星や戦略は、このskillの成果物ではない。

## 後続成果物への追跡

`handoff.downstream`に、利用・負荷、品質、クラウド設計へ渡す要求、制約、仮説、未決の問いのIDを関心ごとに記録する。後続はIDと成果物の版を引用し、原文の状態を保つ。上流の根拠主張、要求、制約の意味または版が変わったときは既存IDを黙って上書きせず、正本の版を上げ、後続成果物は参照した版とIDを再確認対象にする。
