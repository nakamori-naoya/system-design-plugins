# discover-requirements

このskillを読み終えたagentは、依頼と要求源から一つの要求発見資料を作り、確認済み要求、導出要件、理由付き設計判断、未決を後続の負荷・品質・クラウド設計へ渡せる。判断は「観測事実・仮定 → 明示要件・固定制約 → 導出要件 → 設計判断 → 実装詳細」の五段階で境界を引く。要求発見は導出要件まで進み、設計判断は明示・不可避・合意済みのものだけを残し、実装詳細は後続へ送る。

工程の順は[playbook.yml](playbook.yml)の`steps`の宣言順で決まり、同じagentがその順に実行する。`agent_work: invoking_agent`の工程はこのagentの認知工程、`script:`の工程は標準入力の本文から閉じた結果を返す決定論的tool、`playbook:`の工程は外部公開playbook（`grill`、`write-doc`）の直接呼び出しである。本文はインメモリで保持し、JSONも作業用fileも作らない。失敗した工程は成功扱いせず停止し、完了工程、根拠、未決を残す。再開時は最初の未完了工程から続ける。

## 入力

- 依頼。対象、困りごとまたは望む結果、要求源の所在を識別できること。
- 利用者が明示した資料、観測結果、決定記録。各要求源について参照位置と観測時点または版を記録できること。要求源が依頼本文だけなら、根拠を「依頼本文」と記録する。
- `references`（任意）。追加で従う資料の絶対path配列。手順1で最初に読む。プロジェクト固有の規約や文脈（置き場、命名、用語、追加で従う資料）は、対象repositoryのAGENTS.md / CLAUDE.mdとこの`references`で渡される。
- `document_destination`。新規は`{output_directory, name}`（既存の書き込み可能な絶対directoryと`.md`名）、更新は`{update_target}`（既存の要求発見資料の絶対path）のどちらか一方。名前と置き場は利用者の既存資料構成に従い、依頼に無いときだけ`requirements-discovery.md`を初回提案する。版は持たず、更新の履歴はgitが担う。
- 複数成果物で共有する用語があるときは、一つのMarkdown用語定義の絶対pathと版（整数）。共有する用語があるのに用語定義が無ければ、用語定義を参照せずに進み、所有者と配置を推奨付きの未決の問いにする。

入力中の製品名、クラウド名、データベース、キュー、キャッシュ、画面、API、実装方法は要求ではなく、手順4で制約・仮説・設計案のどれかに分類する。

## 判断基準

| 観察対象 | 判定 |
|---|---|
| 根拠の分類 | 観測条件と時点があれば`fact`。決定者・対象・条件が揃えば`agreed_decision`。未検証の予測・期待・提案・推定は`hypothesis`。回答が無く要求または境界の意味を変える問いは`open_question` |
| 要求に昇格できるか | 根拠が`fact`または`agreed_decision`だけで、受益者、合意済み成功観測、検証方法、影響が揃えば`REQ-`。一つでも欠けるか根拠に仮説・未決を含めば仮説または未決のまま |
| Howの置き場 | 決定権者・対象範囲・決定時点が揃った必須手段は`constraint`（`CON-`）。望む結果を満たすか未検証の手段は`hypothesis`。比較・選定を後続へ委ねる候補は設計案として「後続設計で決める論点」の送り先へ送る |
| 導出要件になるか | 実現手段を外しても成り立つ「避けるべき結果と必要な成果」であれば`DRV-`。製品名、RPC項目、エラーコード、表、キュー、再試行回数を含む記述は実装詳細として後続へ送る |
| 導出要件の確からしさ | 確定事実または合意済み決定だけから導ければ確定。推定を含めば仮説として特性の根拠状態を`hypothesis`にする |
| 設計判断を残すか | 利用者が合意した方式（`agreed_decision`の根拠）、または確認済み導出要件から論理的に不可避な方式（`DRV-`を根拠）だけ`DEC-`へ。それ以外の方式は後続設計で決める論点 |
| 操作の種別 | 状態変更を意図する操作は`コマンド`、読み取り専用は`クエリ`。コマンド成功の事実はコマンドイベント、読み取り成立の事実はクエリイベント、時刻・期限到達の事実は時間イベント、内部処理の観測事実はシステムイベント |
| 対になる操作 | 開始／解除、登録／取消の対があれば相互参照、無ければ`なし`、判断できなければ未決の問い |
| スコープ | 提供価値・実装必須・設計説明のみ・対象外の4区分が同じ意味を含まず、対象システムと外部主体の責任境界を説明できる |
| 用語 | 共有語は用語定義の所在・版と日本語の推奨用語名だけを参照する。定義本文は要求発見資料へ複製しない |
| 問いの選定 | 依頼と要求源を読めば分かることは問わない。答えで要求、境界、受入観測、後続の判断が変わる問いだけを、成果を左右する順に選ぶ |

## 手順

### 1. 要求源を根拠に分ける

`references`の資料と要求源を読み、各根拠へ`SRC-` IDを付け、出典、観測時点、根拠状態（`fact` / `agreed_decision` / `hypothesis`）を記録する。後続のすべての項目が一つ以上の根拠IDへ戻れる状態にする。所在・時点・責任者が欠ける主張は、欠けた情報と影響先を未決として残す。

### 2. 受益者、目的、観測を分ける

受益者とその他のステークホルダーを分け、目的を「誰が、どの状態から、どの業務結果を必要とするか」で記録する。成功と失敗は、誰が何を観測できるかとして別々に記録する。画面表示、API応答、利用技術は業務結果ではない。観測主体または結果が根拠から一意に決まらなければ、最も筋の良い候補を仮説として置き、決める問いを推奨付きの未決の問いへ結ぶ。受益者と目的のどちらも依頼と要求源から識別できないときは、要求発見の対象が無いので止まる。

### 3. スコープとシステム境界を確定・保留し、スコープ予算で閉じる

提供価値、実装必須、設計説明のみ、対象外の4区分と、対象システムの責任、外部主体の責任を列挙する。規制、契約、組織、技術の制約は要求や目的と分けて制約にする。実装期間、チーム規模、利用できる外部基盤、ローカルで再現する範囲、実装して検証する範囲を予算として書く。所有者が未決の責任は対象システムへ寄せず、境界を変える未決は影響IDと停止する後続判断を付けて未決の問いにする。

### 4. 入力中のHowを分類する

[要求発見資料の契約](references/requirements-contract.md)の「手段指定（How）の分類」を読み、判断基準に従って制約、仮説、設計案へ分け、原文、分類理由、根拠ID、送付先を追跡できるようにする。決定か提案か判定できないときは`hypothesis`に分類し、分類が要求または後続設計を変えるなら、その違いを確かめる問いを推奨付きの未決の問いへ結ぶ（成果を左右する問いは手順9で問う候補になる）。

### 5. 確認済み要求を作る

一つの必要性ごとに`REQ-` IDを付け、受益者、必要な成果、検証方法、根拠（`SRC-`と根拠状態）を持たせる。各要求から根拠、受入観測、検証方法、影響へ双方向に辿れる状態にする。

### 6. コマンド、クエリ、イベントを棚卸しする

[要求発見資料の契約](references/requirements-contract.md)の「操作とイベントの分類」を読む。対象内の各操作を判断基準の種別へ分け、各コマンドから成功時のコマンドイベント、各クエリから状態変更を伴わないクエリイベントを追跡できるようにする。対になる操作を反証し、対象内・対象外・設計説明のみ・未決のどれかを明示する。無変更、拒否、失敗の扱いが根拠から決まらないときは、状態・コード・再試行方法を決めずに未決の問いへ結ぶ。操作名は用語定義の推奨用語名をそのまま使う。

### 7. サービス特性から導出要件を作る

[要求発見資料の契約](references/requirements-contract.md)の「導出要件と設計判断」を読む。負荷、保持、分布の偏り、整合性、障害波及、再試行などのサービス特性が明示要求だけでは表せない失敗を生むとき、入力に直接書かれていないことを理由に落とさず、特性（根拠IDと根拠状態）→ 失敗リスク → 必要な成果 → 設計への影響 → 見直し条件を一つの因果として導く。導いた内容は追跡の表だけに閉じず、読者向け本文へ「サービス特性から必要になる性質」が分かる自然な見出しと文章で残す。`DRV-` IDは後続資料との追跡が必要なときに追跡の表へ置き、本文の構成をID中心にしない。定量情報が無ければフェルミ推定で桁を置き、定義・根拠種別・計算・時間窓・確度・再確認条件を持つ仮説として記録する。

### 8. 理由付き設計判断と実装詳細を分離する

判断基準に従い、`DEC-`には根拠（`agreed_decision`の`SRC-`または`DRV-`）、採用理由、見直し条件、後続責務を付ける。「よく使われる」「高性能そう」は理由にならない。利用者の選択で方式が変わるときは、その方式を`DEC-`へ入れず後続設計で決める論点に留め、選択を求める問いを推奨付きの未決の問いへ結ぶ。

### 9. 成果を左右する問いをgrillで解消する

手順1〜8で残った未決のうち、判断基準「問いの選定」に従って問う候補を選び、それぞれに理由付きの推奨を添えて`questions`にし、`topic`、`context`（purpose / audience / boundary）、`references`（入力の`references`をそのまま）とともに公開playbook `grill`へ渡す。問い方、上限、一覧への合意はgrillの公開契約に従う。

返った`decisions`は本文の該当箇所へ確定した根拠として反映する。返った`open_questions`は`state`が`open`なら推奨（`reason`）を仮置きし、本文の該当箇所へ`hypothesis`として書き、「後続設計で決める論点」へ`REQ-HYP-` / `REQ-OQ-`の行として推奨・根拠・採らなかった解釈・検証計画を書く。事実や`agreed_decision`へ昇格させない。`withdrawn`は取り下げ理由を本文に残す。

同じ実行でgrillを再び呼ぶのは、利用者が求めた場合か、その決定なしでは手順10の本文を組み立てられない場合だけである。それ以外の残った未決は、保存した成果物とともに推奨を添えて示し、利用者が成果物を見てから確かめる。

### 10. 本文を組み立てる

保存したい要求発見資料の本文を、write-docの`requirements-discovery`型のtemplateと見本に従ってインメモリで組み立てる。見出しは読み手が判断に使う単位で名付け、要求、失敗時の扱い、サービス特性から必要になる性質、固定制約、対象範囲、完了の判断、後続で決めることを、因果が読める順に文章で書く。冒頭は、誰が何を得られるか、今回の範囲、何を満たせば完了かを、読み手の既知の語で言い切る段落にする。後続資料がIDで参照する`REQ-` / `DRV-` / `CON-` / `DEC-`と`REQ-HYP-` / `REQ-OQ-`は、write-docの公開契約「検査が読む目印」の追跡の表に書く。IDごとの定型の見出しを本文の主構成にしない。用語定義を参照するときは、`用語定義: <絶対path> 版: <整数>`の行と`推奨用語名:`の行を、write-docの公開契約「検査が読む目印」に従って一つずつ書く。置く見出しは問わない。

### 11. 本文を検査する

本文を標準入力で`scripts/requirements.py`へ渡す。渡し方の例:

```bash
python3 scripts/requirements.py check <<'MD'
# 要求発見資料 — <対象>
...本文...
MD
```

| 呼び出し | 入力 | 出力 | 失敗の観測 | 失敗時 |
|---|---|---|---|---|
| `python3 scripts/requirements.py check < <本文>` | 標準入力の本文だけ | 終了code 0、stdoutに`verified: true`、`status`（`ready` / `unresolved`）、REQ / DRV / DEC / CON / 仮説 / 未決のID一覧のJSON | 終了code 2、stderrに`FAIL: <理由>`（冒頭の本文段落、空の節、追跡の表の有無と数、IDの形式と一意性、未決の状態とIDの種別のどれか） | 手順10へ戻って本文を直す。検査を緩めず、分類・未決・受入観測を昇格させて通さない。理由が入力の欠落（受益者・目的が無い等）なら止まる |

用語定義を参照したときは、package共有のtool`../../scripts/terminology.py`で用語定義との整合を検査する。この検査は保存後の要求発見資料のpathを受ける。

| 呼び出し | 入力 | 出力 | 失敗の観測 | 失敗時 |
|---|---|---|---|---|
| `python3 ../../scripts/terminology.py check --terminology <用語定義の絶対path> --artifact <保存した要求発見資料の絶対path>`（`--artifact`は複数可） | 用語定義Markdownと参照側の要求発見資料Markdown | 終了code 0、stdoutに用語定義の絶対path | 終了code 2、stderrに`FAIL: <理由>`（`用語定義:`の行が無いか二つ以上、版・所在の不一致、用語定義にない推奨用語名、コマンド・クエリの操作名が用語定義の同じ種別に無い、推奨用語名の重複、種別の行が無いか未知の種別の用語） | 理由を変えずに返して停止する。用語の定義を要求発見資料へ複製して通さない |

### 12. write-docへ渡して保存する

検査済み本文を`material: [{kind: text, content: <本文>}]`、`document_type: requirements-discovery`、`document_destination`の保存先（`output_directory`と`name`、または`update_target`）、`references`（入力の`references`をそのまま）として`write-doc`へ渡す。結果が`status: completed`なら`path`を`requirements_document_path`にする。`status: failed`なら`reason`をそのまま報告して停止し、部分保存を完成文書として扱わない。

### 13. 読み戻して確かめる

保存した資料を全文読み、手順11で検査した本文と同じID、根拠状態、未決、statusを保っていることを確かめる。用語定義を参照したときはここで手順11の`terminology.py`を実行する。欠落や昇格があれば`failed`として資料pathと理由を報告する。

## 停止条件

止まるのは次のときで、それ以外の判断の揺れや資料の不足では止まらない。

- 受益者と目的のどちらも依頼と要求源から識別できず、要求発見の対象が無い。
- 依頼の中心がユーザージャーニー、ドメイン、データモデル、技術方式、クラウド選定で、要求発見の目的が無い。要求発見を完了と報告せず、該当しない理由と適切な別入口を返す。
- `document_destination`が未指定、相対path、または両方式の併記で、保存先を確認できない。
- `grill`が`failed`を返した、`requirements.py`が入力の欠落を理由に2を返し本文を直しても成り立たない、`terminology.py`または`write-doc`が失敗した。理由を変えずに返す。

止まるときは確定した根拠を残し、止めた判断、必要な入力または確認、回答者または確認方法、影響するID、再開に必要な入力を返す。

grillの回答・合意待ちは継続待ちであり、完了でも失敗でもない。待つ間は要求発見資料を保存しない。

判断の揺れや資料の不足では、その時点の根拠から最も筋の良い仮説を立てて進む。

- 受益者、目的、責任範囲、スコープに複数の解釈があり得る: 最も筋の良い解釈を採り、根拠を`hypothesis`にし、採らなかった解釈と影響IDを推奨付きの未決の問いへ残す。
- 要求源の参照位置または状態が分からない: 根拠を「依頼本文」または分かる範囲の所在で記録し、事実ではなく`hypothesis`に分類する。
- Howが合意済み制約か未決の提案か判定できない: `hypothesis`に分類し、分類が要求または後続設計を変えるなら未決の問いへ結ぶ。
- 用語定義が無い: 用語定義を参照せずに進み、所有者と配置を未決の問いにする。

仮説は仮説と分かる形で要求発見資料に書き、根拠の無いことを事実として書かない。

## 出力

- 要求発見資料: write-docが返した`requirements_document_path`（requirements-discovery型のMarkdown）。根拠、受益者・目的、サービス特性と導出要件、理由付き設計判断、保持、固定制約、スコープ、コマンドとクエリ、用語、後続設計で決める論点、観測可能な完了を含む。JSON資料は持たない。
- 公開結果: `status`（`ready`または`unresolved`）、`decisions`、`open_questions`（推奨付き）、`hypotheses`、`requirements_document_path`。
- 報告: 要求発見資料の絶対path、status、確認済み要求数、仮説数、問うた問いと回答、推奨を仮置きした未決の問い、後続利用の可否、実行した検証（`requirements.py`の結果、`terminology.py`の実行有無）、未検証範囲。

完了とは、資料が保存され読み戻しで検査済み本文と意味が一致し、statusが`ready`または`unresolved`であることをいう。`unresolved`は保存完了であり、未決の影響先が後続利用可能であることを意味しない。

## 責務の外

ユーザージャーニー、ユースケース、ドメインルール、BDDシナリオ、エンティティ、論理表、列、キー、DDL、索引、画面、API、構成要素、技術方式、クラウド・サービス、リージョン、IaC、利用負荷や品質目標の値、プロダクトの北極星や戦略は、このskillの成果物ではない。

## 後続成果物への追跡

「後続設計で決める論点」の送り先と「観測可能な完了」に、利用・負荷、品質、クラウド設計へ渡す要求、制約、仮説、未決の問いのIDを残す。後続は要求発見資料の絶対pathとIDを引用し、原文の状態を保つ。上流の根拠、要求、制約の意味が変わったときは既存IDを黙って上書きせず、`update_target`で要求発見資料を更新し、後続成果物は参照したIDを再確認対象にする。
