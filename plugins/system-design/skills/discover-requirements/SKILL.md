# discover-requirements

依頼された型の資料を一本、write-doc で書いて保存する。三つの型は後続のクラウド設計へ渡す入力であり、一つの判断は一つの型だけが持つ。

要件は、誰がどの状態から何を得るか、成功と失敗をどう観測するか、範囲と境界、固定制約、サービス特性から導いた要件の因果を持つ。数値の詳細は持たず、利用負荷と品質要求の ID を引いて要約するだけにする。利用負荷は値と偏りを持つ。規模、平均・ピーク・突発の到着率、偏りと一操作からの増幅、データ量と保持期間と増加の値がこれに当たる。品質要求は守る性質と頻度の制限を持つ。閾値、上限を超えたときに拒むか遅らせるか、消去・匿名化・法的保全で守ることがこれに当たる。同じ数字を二つの型へ書き写さない。二か所に置くと、片方だけが直されて食い違うからである。

型ごとの判断は、書く型の reference だけを読む。[要件](references/requirements-discovery.md)、[利用負荷](references/workload-model.md)、[品質要求](references/quality-requirements.md)である。

## 外しやすい判断

根拠は四つの状態に分け、混ぜない。観測の条件と時点がある `fact`、決めた人・対象・内容がある `agreed_decision`、予測や推定や提案の `hypothesis`、答えで結論が変わる `open_question` である。仮説を事実や合意へ格上げしない。利用者が「とりあえずこの値で」と暫定利用を認めても、分類は仮説のままである。業界標準、クラウドの仕様値、現在の実績は、それだけでは目標の合意にならない。

手段（How）は要求ではない。入力にある製品名、クラウド名、データベース、キュー、画面、API は、決めた人・範囲・時点が揃えば固定制約、満たすか未検証なら仮説、後続で比べる候補なら設計案のどれかに分け、要求や性質の文へ混ぜない。

数値は、単位、時間窓、母集団、根拠と一組にして初めて使える。一つでも欠ければ未決にする。平均に一般的な倍率を掛けただけのピークは、対象の根拠が無いので未決である。

語は、業務知識（domain-rule）の資料のユビキタス言語をそのまま使う。無い語が要るときは推測で作らず、業務知識への提案として報告する。用語集の持ち主は bdd-discovery-and-formulation である。

分からないことを推測で埋めない。欠けた情報が資料の結論を変えるなら grill で問うか止まり、変えないなら仮説と明示して進む。

## 作ると深めるは、grill で何を問うかで分ける

新しく作るときは、発見として問う。受益者と目的、境界、値の出どころのように、上流の決定から先に問う。下流の細部を先に決めると、上流の答えで作り直しになるからである。

既存の資料（`update_target`）を深めるときは、反証する主張を一つに決めてから問う。境界の値、時間窓や母集団の食い違い、ピークと平均の取り違え、負荷の仮説を品質の合意の根拠にしていないか、互いに両立しない値（品質要求では `QCON-` の矛盾）を当てる。ID は別の意味に使い回さない。

どちらでも、資料と上流を読めば分かることは問わない。答えで成果が変わる問いだけを、推奨と理由を添えて grill へ渡す。返った決定は根拠として本文へ反映する。未決のまま残ったものは推奨を仮に置き、仮説か未決として本文と追跡の表に書き、合意へ昇格させない。

## 書いて保存し、保存した資料を一回検査する

write-doc に、組み立てた本文を `material`、型の名前を `document_type`、保存先（新規なら `output_directory` と `name`、更新なら `update_target`）として渡す。型の template が示す論点と、検査が読む目印（追跡の表、ID、状態の値）に従う。

保存した資料を、型に合う検査に一回かける。上流の資料は `--upstream` に絶対パスで渡す。

```bash
python3 scripts/requirements.py check < <保存した要件の資料>
python3 scripts/workload.py check --upstream <要件の資料> < <保存した利用負荷の資料>
python3 scripts/quality.py check --upstream <要件の資料> --upstream <利用負荷の資料> < <保存した品質要求の資料>
```

検査が見るのは、追跡の表があること、ID の形と一意性、状態の値、上流の ID に届くことだけである。失敗したら理由を読んで資料を直し、`update_target` で保存し直して、もう一度かける。検査を通すために分類や状態を変えない。数値の妥当性、因果の成否、区分の網羅は、読んで評価する。

## 止まるとき

型の対象が識別できないときは止まる。要件なら受益者と目的、利用負荷なら利用者・行為・イベントと母集団、品質要求なら守る業務結果と対象システムの境界である。利用負荷と品質要求は要件の資料が上流に要るので、無ければ止まる。保存先が絶対パスで一つに決まらないとき、grill・write-doc・検査が失敗したときも、理由を変えずに返して止まる。

依頼の中心がユーザージャーニー、業務ルール、データモデル、クラウド構成なら、この入口の仕事ではないと返す。

## 返すもの

保存した資料の絶対パス、検査が返した `status`（仮説や未決が残れば `unresolved`、無ければ `ready`）、grill で決まったこと、推奨を仮に置いた未決を返す。`unresolved` は保存が終わったことを示すだけで、未決の影響先を後続へ渡してよいことを意味しない。
