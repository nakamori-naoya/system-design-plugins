# discover-requirements

依頼された型の資料を一本、write-doc で書いて保存する。二つの型は後続のクラウドの設計へ渡す入力であり、一つの判断は一つの型だけが持つ。

要件は、誰がどの状態から何を得るか、成功と失敗をどう観測するか、作るものと作らないもの、前提にする制約、特性から導いた要件の因果を持つ。非機能要件は、機能をまたいで守る性質を持つ。守る順位、規模と負荷の値と偏り、秘匿、整合、速さの目標、復旧、個人情報と保持、頻度の制限、費用、運用がこれに当たる。同じ値を二つの資料へ書き写さない。二か所に置くと、片方だけが直されて食い違うからである。要件の資料は、値が要るところで非機能要件の資料へリンクする。

型ごとの判断は、書く型の reference だけを読む。[要件](references/requirements-discovery.md)と[非機能要件](references/non-functional-requirements.md)である。

## 外しやすい判断

資料は、読み手が最初の数行と図で結論をつかめる形にする。冒頭で、誰が何を得るか（要件）か、何を最優先で守り何を譲るか（非機能要件）を言い切る。流れ、見える範囲、時間の重なり、順位のように形を持つ内容は、節の冒頭に図を置く。書くのは今のあるべき姿で、検討の経過、会話での指摘、旧案からの変更は書かない。要求ごとの ID と追跡の表は置かない。

根拠の確かさは四つに分け、混ぜない。観測の条件と時点がある事実、決めた人・対象・内容がある決定、予測や推定や提案の見立て、答えで結論が変わる未決である。資料では、これを状態の値ではなく文の言い方（「〜と決めた」「〜と推定する」「仮置き」「未確認」）で書き分ける。見立てを事実や決定へ格上げしない。利用者が「とりあえずこの値で」と暫定の利用を認めても、仮置きのままである。入力の値から計算した値は、計算に使った値のうち最も弱い確かさを継ぐ。

手段（How）は要求ではない。入力にある製品名、クラウド名、データベース、キュー、画面、API は、決めた人・範囲・時点が揃えば前提にする制約、そうでなければ後で比べる候補に分け、要求や性質の文へ混ぜない。

語は、業務知識（business-knowledge）の資料のユビキタス言語をそのまま使う。無い語が要るときは推測で作らず、業務知識への提案として報告する。用語集の持ち主は bdd-discovery-and-formulation である。

分からないことを推測で埋めない。欠けた情報が資料の結論を変えるなら grill で問うか止まり、変えないなら見立てと明示して進む。

## 作ると深めるは、grill で何を問うかで分ける

新しく作るときは、入力を読んでも答えが一つに決まらず、その答えで資料の結論が変わることだけを問う。受益者と目的、範囲、値の出どころ、守る順位は先に確かめるが、入力で決まるものは問いにせず前提として書く。下流の細部を先に決めると、上流の答えで作り直しになるからである。

既存の資料（`update_target`）を深めるときは、反証する主張を一つに決めてから問う。境界の値、時間窓や母集団の食い違い、ピークと平均の取り違え、見立ての負荷を決まった目標の根拠にしていないか、両立しない値を当てる。

どちらでも、答えで成果が変わる論点を grill で問う。返った決定は根拠として本文へ書く。未決のまま残ったものは推奨を仮に置き、仮置きと分かる形で書き、決定へ格上げしない。

## 書いて保存し、保存した資料を一回検査する

write-doc に、組み立てた本文と図を `material`、型の名前を `document_type`、保存先（新規なら `output_directory` と `name`、更新なら `update_target`）として渡す。図は write-doc の書くときの規範に従って draw.io で描き、資料の名前に `.assets/` を付けたディレクトリに置く。

保存した資料を、型の名前と絶対パスを渡して一回検査する。

```bash
python3 scripts/check.py requirements-discovery <保存した要件の資料>
python3 scripts/check.py non-functional-requirements <保存した非機能要件の資料>
```

検査が見るのは、題名と冒頭の本文があること、Mermaid が無いこと、図のファイルが置き場に実在して draw.io の定義を埋め込んでいること、非機能要件では題名のすぐ下に守る順位の図があることだけである。失敗したら資料を直して `update_target` で保存し直し、もう一度かける。書き出した図は画像で目視し、線と文字の重なりを確かめる。最後に入力の主張ごとに資料へ届いたかを確かめ、資料の要求・値・方式から根拠へ戻って、今の判断に要らないものを外す。見立てと未決は消さず、数値の妥当性と因果も読んで評価する。

## 止まるとき

型の対象が識別できないときは止まる。要件なら受益者と目的、非機能要件なら守る業務の結果と対象のシステムの範囲である。非機能要件は要件の資料が上流に要るので、無ければ止まる。保存先が絶対パスで一つに決まらないとき、grill・write-doc・検査が失敗したときも、理由を変えずに返して止まる。

依頼の中心がユーザージャーニー、業務ルール、データモデル、クラウドの構成なら、この入口の仕事ではないと返す。

## 返すもの

保存した資料の絶対パス、検査の結果、grill で決まったこと、推奨を仮に置いた未決を返す。未決が残る資料は、保存が終わったことを示すだけで、未決の影響先を後続へ決まったものとして渡してよいことを意味しない。
