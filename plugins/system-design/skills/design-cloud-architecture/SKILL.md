# design-cloud-architecture

このskillを読み終えたagentは、「どの配置方式とクラウド機能領域を、どの根拠・トレードオフ・障害時の挙動で採用するか」を、選定、比較、決定、構成図、失敗時挙動、追跡を一体として監査できる一つのクラウドアーキテクチャ正本にできる。要求、ユーザージャーニー、ドメイン、論理データモデルは作り直さず、アプリケーション内部設計、IaC、配置も実装しない。

工程順は[工程順序の正本](playbook.yml)が正本で、同じagentが`steps`を宣言順に実行する。`agent_work: invoking_agent`の工程はこのagentの認知工程、`script:`の工程は標準入力の本文と公開入力`provider`と上流正本のpathから閉じた結果を返す決定論的tool、`playbook:`の工程は外部公開playbook（`grill`、`write-doc`）の直接呼び出しである。本文はインメモリで保持し、JSONも作業用fileも作らない。失敗した工程は成功扱いせず停止し、完了工程、根拠、未決を残す。再開時は最初の未完了工程から続ける。

## 入力

- `provider`。`aws`または`gcp`。利用者の依頼または合意済み決定として明示され、その根拠を制約（`CON-`、`agreed_decision`）として記録できること。未指定または他の値なら、推測せず確認を求めて止まる（公開入力の欠落）。
- `requirements_document_path`。要求発見正本の絶対path。`REQ-` / `DRV-`と上流の仮説・未決の参照はこの正本のIDへ到達しなければならない。
- `workload_document_path`。利用負荷モデル正本の絶対path。`WL-` / `DIN-`の参照はこの正本へ到達しなければならない。
- `quality_document_path`。品質要求正本の絶対path。`QR-` / `QCON-`の参照はこの正本へ到達しなければならない。
- 論理設計（`logical_design`）。システム／構成要素の責任境界、データの流れ、外部依存を含む。クラウド製品を前提にしなくてよい。
- 組織、運用、予算、法令・規約順守、所在地、既存契約の制約（`organizational_constraints`）。
- `references`（任意）。追加で従う資料の絶対path配列。手順1で最初に読む。プロジェクト固有の規約や文脈（置き場、命名、用語、追加で従う資料）は、対象repositoryのAGENTS.md / CLAUDE.mdとこの`references`で渡される。
- `document_destination`。新規は`{output_directory, name}`、更新は`{update_target}`（既存のクラウドアーキテクチャ正本の絶対path）のどちらか一方。名前と置き場は利用者の既存資料構成に従い、依頼に無いときだけ`cloud-architecture.md`を初回提案する。版は持たず、更新の履歴はgitが担う。

上流の正本は同等内容でよく、生成方法は要求しないが、ID・根拠状態を失った転記は入力として完成扱いしない。

## 判断基準

| 観察対象 | 判定 |
|---|---|
| 開始できるか | システム境界、確認済み要求1件以上、測定可能な品質要求1件以上、利用・負荷モデル、制約、`provider`を識別できれば開始。配置方式が未決でも、候補比較と未決の問いを持つ正本は保存できるが、実装への引き渡しは後続利用可能にしない |
| 配置方式 | プロバイダー範囲が一件で採用サービスがその中にあれば単一クラウド。独立したプロバイダーが二件以上で責任と障害範囲を分けていればマルチクラウド。クラウドとオンプレミス境界の両方があればhybrid。二プロバイダー名の列挙だけではマルチクラウドにならない |
| 選定項目の状態 | 採用候補、代替案、要求・品質・負荷・制約の根拠IDを持てば`agreed_decision`（合意済み）または`hypothesis`。決める問い（`*-OQ-`）を引き採用候補を`未決`にすれば`open_question`。対象境界に基づく理由があれば`not_applicable`（採用候補は`非該当`） |
| 代替案 | 各選定項目に採用候補と1つ以上の代替案、根拠ID、利点、不利・リスク。人気、慣例、プロバイダー一覧に載っていることは根拠にならない |
| ADR | 判断、候補、根拠ID、結果・トレードオフ、再検討条件を持ち、利用者が合意したものだけ`agreed_decision`。未合意なら`hypothesis`のままにし、正本を実装へ引き渡せる状態にしない |
| 障害・縮退経路 | 起点（`NODE-`）、影響、縮退、検知・復旧、関連IDが揃えば経路として成立。どれかが欠ければ未決 |
| 構成図 | Mermaid `flowchart`を直接編集でき、採用構成の全`NODE-`が図の表示名に現れ、`subgraph`と`end`が対応する。流れは同期・非同期と信頼境界の通過を示す |
| 検証の状態 | 実負荷試験・障害試験・災害復旧訓練を実行していなければ計画。テストデータ、文書レビュー、プロバイダー仕様の読取りは成功の証拠にならない |
| 問いの選定 | 上流成果物と制約を読めば分かることは問わない。答えで配置方式、選定、ADRの採否、障害時の挙動が変わる問いだけを、成果を左右する順に選ぶ |

## 手順

### 1. 上流基準資料、入力providerの根拠、設計根拠を固定する

`references`の資料、上流3正本、論理設計、制約を読む。`provider`を指定した依頼または決定記録を制約`CON-`（`agreed_decision`）として「設計入力と制約」へ載せ、要求、品質、利用・負荷の設計根拠を上流IDと根拠状態付きで載せる。共有語は用語正本の推奨用語名で書く。要求や品質閾値の不足・矛盾は、上流IDを引用した推奨付きの未決の問いにし、その設計根拠を`hypothesis`のまま使う。

### 2. 配置方式の境界を判定する

[クラウドアーキテクチャ契約](references/architecture-contract.md)の「配置方式境界」を読み、判断基準に従って配置方式を冒頭とリージョン/AZの行に書く。決め切れないときは根拠が最も強い方式を候補とし、採らなかった方式を未決の問いへ残す。

### 3. 選定項目ごとに代替案を比較する

[クラウドアーキテクチャ契約](references/architecture-contract.md)の「選定と代替案」を読む。12選定項目（プロバイダー、リージョン/AZ、計算処理、ネットワーク、ストレージ、データベース、メッセージング、ID管理、エッジ、可観測性、バックアップ/DR、デリバリー）を各1行、判断基準の状態で扱う。根拠を補えない選定は`open_question`へ戻す。プロバイダー行は入力`provider`と一致させ、根拠IDに手順1の`CON-`を含める。

### 4. 採用判断をADRへ固定する

各主要選定を最低一件の`ADR-`へ結び、判断基準の項目を記録する。後続利用可能な正本は`agreed_decision`のADRを最低一件持つ。

### 5. 障害・縮退経路を設計する

構成要素停止、可用性ゾーン障害、外部依存遅延、メッセージ滞留などの少なくとも一件について`FAIL-` IDを付け、判断基準の項目を記録し、通常の流れと障害・縮退経路を区別する。

### 6. 編集可能なインフラ構成図を作る

[クラウドアーキテクチャ契約](references/architecture-contract.md)の「図の観測可能性」を読む。`flowchart`で始まるMermaid記法を`## インフラ構成図`の1つのブロックに書き、「採用構成」の全`NODE-`を表示名に含める。アプリケーションのクラスやメソッド内部はインフラのノードにならない。

### 7. 要求トレーサビリティを閉じる

各要求・負荷・品質のIDから、ADRと図ノードと検証方法へ辿れる行を「要求トレーサビリティ」に書く。全`ADR-`と全`NODE-`がどこかの行に現れる状態にする。検証は実行していなければ計画として書く。

### 8. 成果を左右する問いをgrillで解消する

手順1〜7で残った未決のうち、判断基準「問いの選定」に従って問う候補を選び、それぞれに理由付きの推奨を添えて`questions`にし、`topic`、`context`（purpose / audience / boundary）、`references`（入力の`references`をそのまま）とともに公開playbook `grill`へ渡す。問い方、上限、一覧への合意はgrillの公開契約に従う。

返った`decisions`は本文の該当箇所へ確定した根拠として反映する。返った`open_questions`は`state`が`open`なら推奨（`reason`）を仮置きし、選定なら`open_question`の行（採用候補`未決`）に候補として添え、ADRなら`hypothesis`のまま本文へ書き、「仮説と未決」へ`ARC-HYP-` / `ARC-OQ-`の行として推奨・根拠・採らなかった代替案・検証計画を書く。`agreed_decision`へ昇格させない。`withdrawn`は取り下げ理由を本文に残す。

同じ実行でgrillを再び呼ぶのは、利用者が求めた場合か、その決定なしでは手順9の本文を組み立てられない場合だけである。それ以外の残った未決は、保存した成果物とともに推奨を添えて示し、利用者が成果物を見てから確かめる。

### 9. 本文を組み立てる

クラウドアーキテクチャ正本の本文を、write-docの`cloud-architecture`型のtemplateが定める記法（H2見出しの名前と順序、表の列、12選定項目の名前、`NODE-` / `ADR-` / `FAIL-` / `CON-` / `ARC-HYP-` / `ARC-OQ-`のID、状態の機械値、mermaidブロック）でインメモリに組み立てる。冒頭は、どのプロバイダーとどの構成を第一候補にし、誰がどの判断へ渡すか、未決が残るなら実装へ渡せる最終決定ではないことを、読み手の既知の語で書いた段落にする。以降は設計入力と制約、代替案比較、採用構成、ADR、インフラ構成図、障害・縮退経路、要求トレーサビリティ、仮説と未決、この資料に書かないものの順に書く。上流の未決を継続する行は上流のID（例`QR-OQ-001`）をそのまま使う。

### 10. 本文を検査する

本文を標準入力で、`provider`を`--provider`で、上流3正本を`--upstream`で`scripts/architecture.py`へ渡す。渡し方の例:

```bash
python3 scripts/architecture.py check --provider aws \
  --upstream /absolute/path/to/requirements-discovery.md \
  --upstream /absolute/path/to/workload-model.md \
  --upstream /absolute/path/to/quality-requirements.md <<'MD'
# クラウドアーキテクチャ — <対象>
...本文...
MD
```

| 呼び出し | 入力 | 出力 | 失敗の観測 | 失敗時 |
|---|---|---|---|---|
| `python3 scripts/architecture.py check --provider <aws\|gcp> --upstream <要求発見正本> --upstream <利用負荷モデル正本> --upstream <品質要求正本> < <本文>` | 標準入力の本文、公開入力provider、上流正本のpath | 終了code 0、stdoutに`verified: true`、`status`（`ready` / `unresolved`）、provider、根拠制約、NODE / ADR（採用済み）/ FAIL / 未決の選定項目 / 仮説 / 未決のID一覧のJSON | 終了code 2、stderrに`FAIL: <理由>`（`--provider`不正、H2の集合と順序、agreed_decisionの`CON-`欠落、プロバイダー行の不一致、12選定項目と状態の規則、ID一意性と参照到達、mermaidに無い`NODE-`、`subgraph`/`end`不対応、追跡に無い`ADR-`/`NODE-`、`open_question`の選定が問いへ結ばれていないのどれか） | 手順9へ戻って本文を直す。検査を緩めず、プロバイダーを仮選定せず、根拠・代替案・図要素を補って通さない。理由が入力の欠落（`provider`や上流正本が無い等）なら止まる |

用語正本との整合はこの型の正本ではscriptで検査しない。用語正本があるときは、本文の語が推奨用語名と一致するかを手順12でagentが読んで確かめる。

### 11. write-docへ渡して保存する

検査済み本文を`material: [{kind: text, content: <本文>}]`、`document_type: cloud-architecture`、`document_destination`の保存先、`references`（入力の`references`をそのまま）として`write-doc`へ渡す。`status: completed`なら`path`を`architecture_document_path`にする。`status: failed`なら`reason`をそのまま報告して停止する。

### 12. 読み戻して確かめる

保存した資料を全文読み、手順10で検査した本文と同じID、選定状態、ADR、図、未決、statusを保っていることを確かめる。欠落や昇格があれば`failed`として資料pathと理由を報告する。

## 停止条件

止まるのは次のときで、それ以外の判断の揺れや資料の不足では止まらない。

- `provider`が未指定、または`aws`／`gcp`以外である。
- 要求発見・利用負荷・品質要求の正本のいずれかが入力に無く、比較の対象が無い。
- 上流成果物が別の対象システムを指しており、同一対象として扱えない。
- 論理設計が無く、境界、ノード、流れ、外部依存のどれも識別できない。
- 依頼の中心が上流要求の再発見、論理データモデル、アプリケーション内部設計、IaC実装、配置である。入力の所有者へ未決を返し、入力成果物をこのskill内で修正して設計を進めない。
- `document_destination`が未指定、相対path、または両方式の併記で、保存先を確認できない。
- `grill`が`failed`を返した、`architecture.py`が入力の欠落を理由に2を返し本文を直しても成り立たない、`write-doc`が失敗した。理由を変えずに返す。

止まるときは比較済み代替案と確認済み設計根拠を残し、止めた選定／ADR、必要な入力または確認、回答者、影響先、再開条件を返す。

grillの回答・合意待ちは継続待ちであり、完了でも失敗でもない。待つ間は正本を保存しない。

判断の揺れや資料の不足では、その時点の根拠から最も筋の良い仮説を立てて進む。

- 上流正本の版・状態が分からない: 読んだ内容のハッシュと観測時点を記録し、その設計根拠を`hypothesis`にして版の確認を推奨付きの未決の問いにする。
- 配置方式が決め切れない: 根拠が最も強い方式を候補として代替案に置き、採らなかった方式を未決の問いへ残す。
- 選定項目を要求、品質、利用・負荷、制約へ追跡できない: その項目を`open_question`にし、推奨する候補と欠けている根拠を未決の問いへ結ぶ。
- 図の一部の要素（同期方式、可用性単位など）を識別できない: 識別できた要素で図を作り、欠けた要素を未決の問いにする。

仮説は仮説と分かる形で正本に書き、未決の選定を採用済み、未合意のADRを`agreed_decision`へ変えない。

## 出力

- 正本: write-docが返した`architecture_document_path`（cloud-architecture型のMarkdown）。設計入力と制約（入力providerの根拠制約を含む）、代替案比較、採用構成、ADR、編集可能なインフラ構成図、障害・縮退経路、要求トレーサビリティ、仮説と未決を含む。JSON正本は持たない。
- 公開結果: `status`（`ready`または`unresolved`）、`decisions`、`open_questions`（推奨付き）、`hypotheses`、`architecture_document_path`。
- 報告: 正本の絶対path、status、配置方式、採用済み・未決の選定項目、採用・棄却代替案、合意済み・仮説のADR、問うた問いと回答、推奨を仮置きした未決の問い、検証状態、実行した検証（`architecture.py`の結果）、未検証範囲（実配置・負荷試験・障害試験・災害復旧訓練）。

完了とは、正本が保存され読み戻しで検査済み本文と意味が一致し、statusが`ready`または`unresolved`であり、`provider`が`aws`または`gcp`で根拠制約と採用選定へ追跡でき、12選定項目が評価され、比較、ADR、障害・縮退経路、要求トレーサビリティ、編集可能なMermaid図があることをいう。`unresolved`は比較と保存の完了であり、未決の選定、未合意のADR、未決の問いの対象について実装へ引き渡せる状態を意味しない。

## 責務の外

要求、受入条件、ユーザージャーニー、ドメインルール、BDD、品質閾値、利用・負荷値の作り直し、エンティティ、表、列、キー、索引、論理データモデルの変更、アプリケーション内部のモジュール、クラス、メソッド、アルゴリズム、APIデータ量の設計、Terraform、CloudFormation、配置マニフェスト、アプリケーションコードの実装、クラウドへの配置、アカウント作成、契約、購入は、このskillの成果物ではない。

## 後続成果物への追跡

「要求トレーサビリティ」とADRにREQ / QR / WL / CON、選定、検証のIDを残す。実装や検証の後続成果物はアーキテクチャ正本の絶対pathとIDを引用し、仮説の設計根拠と計画済みの検証を確定扱いしない。上流成果物、プロバイダー条件、価格、サービス機能、障害前提が変わったときは`update_target`で正本を更新し、再比較する選定、代替案、ADR、障害、構成図ノード、検証を「仮説と未決」へ記録する。古いプロバイダー仕様や価格は再確認してから引き継ぐ。
