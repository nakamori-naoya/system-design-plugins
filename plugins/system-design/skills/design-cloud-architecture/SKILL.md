# design-cloud-architecture

要件と非機能要件の資料を根拠に、どの配置方式とどのサービスを、何と比べて、どんな得失と障害時の振る舞いで採るかを決め、write-doc の `cloud-architecture` 型で保存する。上流の資料、業務ルール、データモデルは作り直さず、IaC も実装しない。上流に不足や矛盾を見つけたら、自分で埋めずに、上流の資料への提案と未決として残す。

配置方式、比べる機能領域、構成図の描き方は [クラウドアーキテクチャの判断](references/architecture-judgment.md) を読む。

## 外しやすい判断

資料は、構成図と冒頭の数行で、何がどこで動き、なぜその構成かが分かる形にする。書くのは決めた構成のあるべき姿で、検討の経過、決定の番号、見送った案の時系列は書かない。比べた候補は、選んだ理由と見直す条件に要る分だけ本文に残す。

provider は推測しない。`aws` か `gcp` を利用者が明示したときだけ始め、その指定を前提にする制約として書く。未指定やほかの値なら、確かめを求めて止まる。

選定には代替案と根拠が要る。構成を左右する領域ごとに、選んだもの、一つ以上の代替案、要件・非機能要件・制約のどれに基づくか、得るものと失うものを本文で比べる。人気、慣例、プロバイダーの一覧に載っていることは根拠にならない。根拠を補えない選定は言い切らず、未決にして何が決まれば選べるかを書く。対象の範囲の外にある領域は、外にある理由を一文書いて比べない。

利用者が合意した選定だけを決まった構成として書く。合意していない選定は、推奨であることと見直す条件を添えて書き、作り始めてよい決定として渡さない。

障害時の振る舞いは、止まる場所、影響、縮退のしかた、検知と復旧を、非機能要件の守る順位に結び付けて書く。負荷試験、障害試験、復元の訓練をしていなければ、確かめ方は計画と書く。仕様を読んだことやテストデータは、成功の証拠にならない。料金と仕様は、確かめた日と出典を添えるか、未確認と書く。

分からないことを推測で埋めない。欠けた情報が構成の結論を変えるなら grill で問うか止まり、変えないなら見立てと明示して進む。

## 問い方

答えで配置方式、選定、障害時の振る舞い、費用が変わる論点を grill で問う。返った決定は根拠として本文へ書き、未決のまま残ったものは推奨を仮に置いて、推奨と分かる形で書く。既存の資料（`update_target`）を深めるときは、反証する選定を一つ決め、上流の値や前提が変わったときに崩れないかを当てる。

## 書いて保存し、保存した資料を一回検査する

構成図を draw.io で描き、PNG に書き出して目で確かめてから、write-doc に、本文と図を `material`、`document_type: cloud-architecture`、保存先（`output_directory` と `name`、または `update_target`）として渡す。図は資料の名前に `.assets/` を付けたディレクトリに置き、題名のすぐ下に置く。

保存した資料を一回検査する。

```bash
python3 scripts/architecture.py <保存したインフラ構成の資料の絶対パス>
```

検査が見るのは、題名のすぐ下に draw.io の定義を埋め込んだ構成図があること、図のファイルが置き場に実在すること、Mermaid が無いこと、題名と冒頭の本文があることだけである。失敗したら資料を直して `update_target` で保存し直す。最後に上流の要件と障害時の結果から構成の抜けを探し、図の各要素と選定から根拠へ戻って、今は要らないサービスを外す。採用案の実現性と代替案の得失は資料を読んで確かめ、未決を方式で埋めない。

## 止まるとき

provider が `aws` か `gcp` で明示されていない、要件か非機能要件の資料が無い、上流が別の対象システムを指している、論理設計から境界も構成要素も流れも識別できない、保存先が絶対パスで一つに決まらない、grill・write-doc・検査が失敗した、のどれかで止まり、理由を変えずに返す。依頼の中心が要求の発見、データモデル、アプリケーションの内部設計、IaC の実装なら、この入口の仕事ではないと返す。

## 返すもの

保存した資料と構成図の絶対パス、検査の結果、配置方式、採用した選定と退けた代替案、利用者が合意した選定と推奨のままの選定、grill で決まったこと、推奨を仮に置いた未決、まだ実施していない検証を返す。
