# クラウドアーキテクチャの判断

## 配置方式は、プロバイダーの名前の数ではなく、責任と障害の範囲で見分ける

採用するサービスがすべて一つのプロバイダーの中にあれば単一クラウドである。マルチクラウドと言えるのは、独立した二つ以上のプロバイダーがそれぞれサービスの責任と障害の範囲を受け持ち、それを図に描けるときだけである。バックアップを別のプロバイダーへ書き出すだけなら、サービスの責任は分かれていないので単一クラウドのままである。「可用性を上げるためにマルチクラウド」と書くなら、障害の独立性、データの整合性、運用のしやすさ、費用を比べていなければならない。

クラウドとオンプレミスの境界が両方あれば hybrid で、接続、信頼境界の通過、運用の責任を描く。オンプレミスとの接続の要件が加わっただけでも hybrid へ切り替え、VPN の製品より先に境界と流れを決める。決め切れないときは、根拠の最も強い方式を候補にして比べ、採らなかった方式を決める問い（`ARC-OQ-`）に残す。

## 比べるのは、構成を左右する領域だけ

機能領域には、リージョンと可用性ゾーン、計算処理、ネットワーク、ストレージ、データベース、メッセージング、ID 管理、エッジ、可観測性、バックアップと災害復旧、デリバリーがある。これは論点を思い出すための案内であって、全部を同じ形で埋める一覧ではない。要件・品質・利用負荷・制約のどれかが答えを左右する領域だけを選んで比べる。

## 構成図は、追跡の表と同じノードを描く

構成図は `flowchart` で始まる Mermaid のブロック一つにする。追跡の表のすべての `NODE-` を、`NODE_EDGE["NODE-EDGE<br/>公開入口"]` のように表示名に含める。公開境界、信頼境界、外部は `subgraph` か外部のノードで示し、`subgraph` と `end` を対応させる。流れは、同期を実線、非同期を点線にし、信頼境界を越える流れにはラベルを付ける。可用性の単位は、配置の判断に効くときだけ `subgraph` で描く。未決の選定は候補のノードとして描き、状態を `open_question` にする。

図にしか無い情報を作らない。図と追跡の表のノードが食い違うと、読み手はどちらが正しいかを確かめる手間を負うからである。アプリケーションのクラスやメソッドは、インフラのノードではない。
