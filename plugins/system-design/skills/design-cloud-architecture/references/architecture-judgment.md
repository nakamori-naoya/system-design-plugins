# クラウドアーキテクチャの判断

## 配置方式は、プロバイダーの名前の数ではなく、責任と障害の範囲で見分ける

採用するサービスがすべて一つのプロバイダーの中にあれば単一クラウドである。マルチクラウドと言えるのは、独立した二つ以上のプロバイダーがそれぞれサービスの責任と障害の範囲を受け持ち、それを図に描けるときだけである。バックアップを別のプロバイダーへ書き出すだけなら、サービスの責任は分かれていないので単一クラウドのままである。「可用性を上げるためにマルチクラウド」と書くなら、障害の独立性、データの整合性、運用のしやすさ、費用を比べていなければならない。

クラウドとオンプレミスの境界が両方あれば hybrid で、接続、信頼の境界の通過、運用の責任を描く。オンプレミスとの接続の要件が加わっただけでも hybrid へ切り替え、VPN の製品より先に境界と流れを決める。決め切れないときは、根拠の最も強い方式を候補にして比べ、採らなかった方式を未決に残す。

## 比べるのは、構成を左右する領域だけ

機能領域には、リージョンと可用性ゾーン、計算処理、ネットワーク、ストレージ、データベース、メッセージング、ID 管理、エッジ、可観測性、バックアップと災害復旧、デリバリーがある。これは論点を思い出すための案内であって、全部を同じ形で埋める一覧ではない。要件、非機能要件、制約のどれかが答えを左右する領域だけを選んで比べる。規模が小さく、どの製品でも処理能力が足りるなら、そう書いたうえで、実際に構成を決めた条件（費用、運用の人数、時刻で動く処理、秘匿）で比べる。

## 分けるかどうかは、分ける理由とまとめる理由を同じ重さで比べる

正しい構成は無く、文脈の中で最も悪くないトレードオフの組を選ぶだけである。処理やデータを別のサービスに分ける理由（変更の範囲と頻度が違う、要る規模や耐障害性が違う、守るものの秘匿が違う）と、一つにまとめる理由（一つのトランザクションで守る決まり、一続きのワークフロー、共有する決まりやコード、データどうしの関係）を、同じ重さで並べる。分ける理由だけを並べると、トランザクションを分散させ、まとめて変えるべきものを別々に変える構成になる。

分けたかどうかは、サービスの数ではなく、独立して動かせる単位の数で見る。同じデータベースを共有する、一つの調停役を全てが同期で呼ぶ、同期でしか呼べない、といった結合が残れば、いくつに分けても一つの単位で、性質を部分ごとに持てない。障害中の相手に同期で依存している限り、分けても耐障害性は上がらない。

データは、書き込むサービスが持つ。二つのサービスが同じデータに書くなら、分けるか、どちらかへ書き込みを任せるか、まとめるかを決める。複数のサービスにまたがる一続きの更新は、通信（同期か非同期か）、一貫性（一度に全てか、後で揃うか）、協調（調停役が指示するか、各自がイベントで動くか）の組で形が決まり、組ごとに結合の強さ、複雑さ、応答の速さ、規模の伸びが違う。慣れた形（同期で一度に全てを揃える形）を既定にせず、非機能要件の守る順位から選び、取り消しの処理が失敗したときの扱いまで書く。

比べた結果は、性質ごとの得失を業務の言葉で書き、選択は利用者に二者択一で問う。「整合を守るために予約の応答が遅くなるのと、速く応答して後で重複を取り消すのとどちらを取るか」のように問うと、利用者は技術の名前を知らなくても決められる。候補ごとの月の費用の見込みも、同じ並びに置く。

## 構成図は、読み手が最初に見るもの

構成図は資料の題名のすぐ下に一枚置く。描くのは、利用者の側、エッジ、クラウドのリージョン、外部のサービスの境界と、構成要素と、主な流れである。同期を実線、非同期を点線、止める・拒むといった守りの動きを別の色の線にし、図のすぐ後の一文で線の読み方を言う。可用性の単位は、配置の判断に効くときだけ描く。決まっていない選定は、候補であることが分かる形で描く。

図にしか無い情報を作らない。図と本文と構成要素の表で、同じ要素に同じ名前を使う。食い違うと、読み手はどちらが正しいかを確かめる手間を負うからである。アプリケーションのクラスやメソッドは、インフラの構成要素ではない。

図は draw.io の XML を書き、draw.io Desktop の CLI で定義を埋め込んだ `.drawio.svg` に書き出す。線が要素を横切る、ラベルが線に重なる、といった崩れは XML を読んでも分からないので、PNG にも書き出して目で確かめ、直してから保存する。要素の数が多いときは、境界ごとに列か行を決めて置き、交差する線には跳び越しの弧（`jumpStyle=arc`）を付ける。
